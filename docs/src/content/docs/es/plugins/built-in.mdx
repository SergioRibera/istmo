El crate `istmo-plugins` viene con el framework y se reexporta como
`istmo::plugins`, así que estos plugins no necesitan otra dependencia.
Tienen dos formas:

- **Streams** — la plataforma (o un publicador Rust en escritorio)
  publica un valor en un [canal de early events](/istmo/es/concepts/frame-protocol/)
  y Rust lo lee. Las instantáneas (batería, red, tema, …) guardan el
  último valor, así que quien lee tarde lo recibe al instante; los deep
  links y los documentos son colas que retienen lo que llega antes del
  primer suscriptor.
- **Llamadas** — un trait `#[istmo::plugin]` con su cliente generado. La
  plataforma implementa el trait; Rust lo llama.

| Cliente | Id del plugin | Forma | Lo publica / implementa |
| ------- | ------------- | ----- | ----------------------- |
| `AppLifecycle` | `istmo.lifecycle` | último valor | el shell nativo de la app |
| `DeepLinks` | `istmo.deeplinks` | cola | el shell nativo de la app |
| `Documents` | `istmo.documents` | cola | el shell nativo de la app; `DocumentsPublisher` en escritorio |
| `SafeArea` | `istmo.safe_area` | último valor | la actividad Android; el view controller iOS o `SafeAreaPublisher` |
| `SystemInfoClient` | `istmo.system_info` | últimos valores | observadores del runtime; `SystemInfoPublisher` en escritorio |
| `DeviceInfoClient` | `istmo.device_info` | último valor | observadores del runtime; `DeviceInfoPublisher` en escritorio |
| `ThemePreferenceClient` | `istmo.theme_preference` | último valor | observadores del runtime; `ThemePreferencePublisher` en escritorio |
| `NetworkStateClient` | `istmo.network_state` | último valor | observadores del runtime; `NetworkStatePublisher` en escritorio |
| `BatteryStateClient` | `istmo.battery_state` | último valor | observadores del runtime; `BatteryStatePublisher` en escritorio |
| `StorageInfoClient` | `istmo.storage_info` | último valor | observadores del runtime; `StorageInfoPublisher` en escritorio |
| `CapabilitiesClient` | `istmo.capabilities` | último valor | observadores del runtime; `CapabilitiesPublisher` en escritorio |
| `PermissionsClient` | `istmo.permissions` | llamadas | backend nativo de la app |
| `NotificationsClient` | `istmo.notifications` | llamadas | backend nativo de la app |
| `AdMobClient` | `istmo.admob` | llamadas (con estado) | backend nativo de la app |
| `ActivityResultsClient` | `istmo.activity_results` | llamadas | backend nativo de la app |
| `TaskSchedulerClient` | `istmo.task_scheduler` | llamadas | backend nativo de la app |
| `ServiceControlClient` | `istmo.service_control` | llamadas | lo usa [`#[istmo::service]`](/istmo/es/writing-plugins/services-workers/) |

## Declara lo que usas

Los crates de plugins se conectan desde sus manifiestos; los integrados
no: lista en `istmo::runtime!` cada cliente integrado que lea la app. El
runtime exige las declaraciones, así que `acquire()` sobre un plugin no
declarado falla con `IstmoError::PluginNotDeclared`.

```rust
use istmo::plugins::{AppLifecycle, DeepLinks, NetworkStateClient, SafeArea};

istmo::runtime!(
    plugins: [AppLifecycle, DeepLinks, NetworkStateClient, SafeArea],
);
```

La lista también decide qué permisos inyecta `istmo-build`: declarar
`NetworkStateClient` añade `android.permission.ACCESS_NETWORK_STATE` al
manifiesto de Android. Ningún otro integrado añade permisos.

## Leer un stream

Cada cliente de instantáneas es un `LatestClient<T>` y cada stream un
`EarlyStream<T>`:

| Método | Devuelve |
| ------ | -------- |
| `Client::acquire()` | cliente sobre el runtime global del proceso |
| `Client::from_runtime(&rt)` | cliente sobre `rt` |
| `client.current()` | `Result<Option<T>, IstmoError>` — `None` antes de la primera publicación |
| `client.current_or_default()` | `Result<T, IstmoError>` (cuando `T: Default`) |
| `client.stream()` | `EarlyStream<T>`: primero el valor retenido, luego cada publicación |
| `stream.recv()` / `stream.recv_async().await` | `Result<T, IstmoError>`, bloqueante / async |
| `stream.try_recv()` | `Option<Result<T, IstmoError>>`, nunca bloquea |

```rust
use istmo::plugins::{LinkKind, NetworkStateClient};

let network = NetworkStateClient::acquire()?;
if let Some(state) = network.current()? {
    let on_wifi = state.online && state.link == LinkKind::Wifi;
}
let updates = network.stream();
while let Ok(state) = updates.recv_async().await {
    render(&state);
}
```

### Quién publica

- **Android** — `IstmoHost.onCreate` (lo llaman `IstmoGameActivity` e
  `IstmoNativeActivity`) arranca `IstmoBuiltinObservers`: la información
  del dispositivo, las capacidades y el almacenamiento se publican una
  vez; la información del sistema, el tema, la red y la batería siguen
  los callbacks del sistema. Las apps que arrancan el runtime por su
  cuenta llaman a `IstmoHost.registerBuiltinObservers(context)`.
- **iOS** — `IstmoApp.run()` crea `IstmoBuiltinObservers` y llama a
  `registerAll()`, con el mismo reparto.
- **Escritorio** — nada publica solo; crea los
  [publicadores de escritorio](#publicadores-de-escritorio) que necesites.

El ciclo de vida, los deep links, los documentos y las insets del área
segura los publica la propia actividad o el app delegate de la app, con
`IstmoRuntime.publishEarlyLatest` / `publishEarlyQueue` o
`IstmoRuntime.publishSafeArea` (Kotlin y Swift). Los payloads usan el
formato de cable del tipo Rust; `examples/android-demo` muestra los
publicadores de ciclo de vida y de deep links.

## Ciclo de vida

`AppLifecycle` lee `LifecycleState`: `Created`, `Started`, `Resumed`,
`Paused`, `Stopped`, `Destroyed`, `LowMemory`, `ConfigurationChanged`
(nombrados según los callbacks de actividad de Android; iOS mapea sus
fases de escena al mismo conjunto). Se publica en `istmo.lifecycle`.

```rust
use istmo::plugins::{AppLifecycle, LifecycleState};

let states = AppLifecycle::acquire()?.stream();
while let Ok(state) = states.recv_async().await {
    if state == LifecycleState::Paused {
        save_draft();
    }
}
```

## Deep links

`DeepLinks` lee una cola de `DeepLink { uri, source, received_at_ms }`
en `istmo.deeplinks`. Los enlaces publicados antes de que haya
suscriptores (un arranque en frío desde un enlace) se retienen — hasta
`DEFAULT_DEEPLINKS_CAPACITY` (16), descartando primero el más antiguo —
y el primer suscriptor los recibe. `DeepLinks::from_runtime_with_capacity(&rt, n)`
elige otra capacidad.

```rust
use istmo::plugins::DeepLinks;

let links = DeepLinks::acquire()?.stream();
while let Ok(link) = links.recv_async().await {
    route(&link.uri);
}
```

## Documentos

`Documents` entrega los archivos que el sistema pide abrir a la app,
como `OpenedDocument { location, display_name, mime_type, origin,
activation_token }`. `location` es `DocumentLocation::Path(String)` o,
para una URI `content://` de Android o una URL con ámbito de seguridad
de iOS, `DocumentLocation::Uri(String)`; `origin` es `Launch`, `Running`
o `Share`. `documents.stream()` entrega los documentos (retiene 32 antes
del primer suscriptor); `documents.activations()` entrega una
`InstanceActivation` cuando un segundo arranque no reenvió ningún
documento, para que la app traiga su ventana al frente.

Los tipos de archivo salen de `[[app.document_type]]` en `istmo.toml`.
En escritorio, `DocumentsPublisher::start` publica los documentos de la
línea de comandos y, con `single_instance`, reenvía los de un arranque
posterior a la instancia en ejecución; ver la
[referencia de istmo.toml](/istmo/es/build-scripts/istmo-toml-reference/#appdocument_type).

```rust
let key = istmo::single_instance!();
match istmo::plugins::DocumentsPublisher::start(&rt, std::env::args_os().skip(1), key.as_ref())? {
    istmo::plugins::Startup::Forwarded => return Ok(()), // la instancia en ejecución los tomó
    istmo::plugins::Startup::Primary(publisher) => run_app(publisher), // mantenlo vivo
}
```

En Android e iOS el runtime no publica documentos: el intent handler o
el app delegate de la app publica cada `OpenedDocument` en la cola
`istmo.documents` (`publishEarlyQueue`, capacidad 32).

## Área segura

`SafeArea` lee `SafeAreaInsets { system_bars, ime, display_cutout }`,
cada uno un `EdgeInsets { top, right, bottom, left }` en puntos lógicos.
`insets.padding()` evita barras y recortes; `insets.view_padding()`
además deja libre el teclado abajo.

```rust
use istmo::plugins::SafeArea;

let padding = SafeArea::acquire()?.current_or_default()?.view_padding();
```

- **Android** — publica desde el listener de window insets de la
  actividad con `IstmoRuntime.publishSafeArea(...)` (doce floats:
  barras del sistema, IME y recorte, cada uno top/right/bottom/left).
- **iOS** — activa la feature `winit-publisher` de `istmo` y llama una
  vez a `istmo::plugins::SafeAreaPublisher::install(&rt)?`;
  luego `tick()` desde el hilo de UI en cada frame: lee las
  `safeAreaInsets` de la ventana principal y publica solo los cambios.
  En otros targets `tick()` no hace nada.
  Las apps cuya UI no es un frame loop de Rust llaman a
  `IstmoRuntime.shared.publishSafeArea(...)` (los mismos doce floats)
  desde `viewSafeAreaInsetsDidChange` y las notificaciones de frame del
  teclado.

## Información del sistema

`SystemInfoClient` agrupa tres canales y dos relojes:

| Método | Devuelve |
| ------ | -------- |
| `current_locale()` / `locale_stream()` | `Locale { bcp47, language, region, script, direction }` |
| `current_timezone()` / `timezone_stream()` | `TimeZone { id, offset_seconds, is_dst, abbreviation }` |
| `current_formats()` / `formats_stream()` | `Formats { uses_24h, first_day_of_week, measurement, temperature_unit, currency_code, decimal_separator, group_separator, calendar }` |
| `uptime_millis()` | `Option<u64>`, milisegundos desde el arranque leídos del reloj del SO en Rust (`None` en targets sin lector) |
| `now_utc_millis()` | `i64`, leído del reloj del sistema en Rust |

Los observadores de Android e iOS publican locale, zona horaria y
formatos; en escritorio lo hace `SystemInfoPublisher`. Los dos relojes no
necesitan publicador.

## Información del dispositivo

`DeviceInfoClient` lee `DeviceInfo { model, manufacturer, os_name,
os_version, arch, form_factor, cpu_cores, ram_total_bytes, screen,
vendor_id }`. `current_or_fallback()` devuelve la instantánea publicada
o `device_info_rust_fallback()` — nombre del SO, arquitectura, form
factor y núcleos según la biblioteca estándar, todo lo demás `None`.

## Preferencias de tema

`ThemePreferenceClient` lee `ThemePreference { color_scheme,
accent_color, high_contrast, font_scale, reduce_motion,
reduce_transparency, bold_text, invert_colors, screen_reader_active }`.
`color_scheme` es `Light`, `Dark` o `Auto`.

## Red, batería, almacenamiento, capacidades

| Cliente | Valor |
| ------- | ----- |
| `NetworkStateClient` | `NetworkState { online, link, metered, expensive, constrained }`; `link` es un `LinkKind` (`None`, `Wifi`, `Cellular`, `Ethernet`, `Vpn`, `Bluetooth`, `Other`) |
| `BatteryStateClient` | `BatteryState { level, charging, power_source, power_saver, thermal_state }`; `level` es `0.0..=1.0` o `None` sin batería |
| `StorageInfoClient` | `StorageInfo { primary_free_bytes, primary_total_bytes, external }` |
| `CapabilitiesClient` | flags de `Capabilities`: `has_biometric`, `has_face_id`, `has_fingerprint`, `has_nfc`, `has_haptics`, `has_camera_front`, `has_camera_back`, `has_gps`, `has_bluetooth`, `has_microphone`, `has_telephony` |

En Android e iOS el almacenamiento y las capacidades se muestrean una
vez al arrancar.

## Publicadores de escritorio

En Linux, macOS y Windows el módulo exporta publicadores en Rust puro.
Cada uno se crea con `install(&rt)` (que falla si el plugin no está
declarado) y publica solo cuando el valor cambió.

```rust
use istmo::plugins::{
    BatteryStatePublisher, CapabilitiesPublisher, DeviceInfoPublisher, NetworkStatePublisher,
    StorageInfoPublisher, SystemInfoPublisher, ThemePreferencePublisher,
};

DeviceInfoPublisher::install(&rt)?.publish();
CapabilitiesPublisher::install(&rt)?.publish();

let mut system = SystemInfoPublisher::install(&rt)?;
let mut theme = ThemePreferencePublisher::install(&rt)?;
let mut network = NetworkStatePublisher::install(&rt)?;
let mut battery = BatteryStatePublisher::install(&rt)?;
let mut storage = StorageInfoPublisher::install(&rt)?;

// Desde el event loop o un temporizador:
system.tick();
theme.tick();
network.tick();
battery.tick();
storage.tick();
```

| Publicador | Llamada | Linux | macOS | Windows |
| ---------- | ------- | ----- | ----- | ------- |
| `SystemInfoPublisher` | `tick()`, sirve en cada frame | entorno + `/etc/localtime` | Foundation | APIs Win32 de locale / zona horaria |
| `DeviceInfoPublisher` | `publish()` una vez | RAM, versión del kernel | versión del SO | RAM, versión del SO |
| `ThemePreferencePublisher` | `tick()`, muestrea como mucho cada 2 s | `gsettings` | `defaults read` | registro `AppsUseLightTheme` |
| `NetworkStatePublisher` | `tick()` | `/proc/net/route` + `/sys/class/net` | Network.framework `nw_path_monitor` | `GetAdaptersAddresses` |
| `BatteryStatePublisher` | `tick()` | `/sys/class/power_supply` | IOKit `IOPSCopyPowerSourcesInfo` + `NSProcessInfo` | `GetSystemPowerStatus` |
| `StorageInfoPublisher` | `tick()` | `statvfs` | `statvfs` | `GetDiskFreeSpaceExW` |
| `CapabilitiesPublisher` | `publish()` una vez | sondeos de `/sys` + `/dev` | todo `false` | todo `false` |

El publicador de tema solo rellena `color_scheme`; el resto de campos
queda con su valor por defecto. En Linux la zona horaria lleva el id con
`offset_seconds = 0` e `is_dst = false`. El almacenamiento lee el
volumen del directorio de trabajo y deja `external` en `None`.

## Llamadas

Permisos, notificaciones, AdMob, tareas programadas y control de
servicios no tienen implementación nativa en el runtime de istmo: el
backend lo pone la app. Sus contratos están en `istmo-plugins-schema`;
pásalos a `istmo-build` para generar los dispatchers Kotlin / Swift y la
interfaz `<T>Backend`, y luego implementa `<T>BackendImpl` (`AdMob` tiene
estado: `AdMobFactoryImpl`). Ver la
[visión general de emit](/istmo/es/build-scripts/emit-overview/) y
[plugins hospedados en nativo](/istmo/es/writing-plugins/native-hosted/).

```rust
// build.rs — con istmo-build e istmo-plugins-schema en [build-dependencies]
fn main() {
    istmo_build::emit_with(istmo_build::AppOpts {
        extra_contracts: vec![
            istmo_plugins_schema::permissions(),
            istmo_plugins_schema::notifications(),
        ],
        ..istmo_build::AppOpts::default()
    });
}
```

Los métodos de los clientes devuelven `Result<T, IstmoError>`; un error
de dominio del backend llega como `IstmoError::PluginError { bytes }`.

### Permisos

`PermissionsClient`:

- `check(permission: String) -> PermissionStatus`
- `request(permissions: Vec<String>) -> Vec<PermissionOutcome>`
- `should_show_rationale(permission: String) -> bool`

`PermissionStatus` es `Granted`, `Denied`, `PermanentlyDenied`,
`NotDetermined` o `NotSupported`; `PermissionOutcome` es
`{ permission, status }`. Los nombres de permiso son los de cada
plataforma.

```rust
use istmo::plugins::{PermissionStatus, PermissionsClient};

let permissions = PermissionsClient::acquire()?;
if permissions.check("android.permission.CAMERA".into()).await? != PermissionStatus::Granted {
    permissions.request(vec!["android.permission.CAMERA".into()]).await?;
}
```

### Notificaciones

`NotificationsClient`:

- `is_authorized() -> bool`
- `request_authorization() -> bool`
- `schedule(request: NotificationRequest) -> NotificationHandle`
- `cancel(id: u32)`

`NotificationRequest { title, body, channel_id, importance,
delay_seconds, tag }`, con `importance` igual a `Min`, `Low`, `Default`
o `High`. `NotificationHandle { id }`. Errores: `NotificationError`
(`PermissionDenied`, `InvalidChannel(String)`, `Scheduler(String)`).

```rust
use istmo::plugins::{NotificationImportance, NotificationRequest, NotificationsClient};

let notifications = NotificationsClient::acquire()?;
if notifications.request_authorization().await? {
    let handle = notifications
        .schedule(NotificationRequest {
            title: "Copia terminada".into(),
            body: "42 archivos subidos".into(),
            channel_id: "backups".into(),
            importance: NotificationImportance::Default,
            delay_seconds: None,
            tag: None,
        })
        .await?;
}
```

### AdMob

`AdMobClient` tiene estado: créalo con
`AdMobClient::acquire_with(AdMobConfig { app_id, test_device_ids,
child_directed_treatment }).await?` (o `from_runtime_with(&rt, config)`).
Los anuncios son [native handles](/istmo/es/writing-plugins/native-handles/):

| Método | Devuelve |
| ------ | -------- |
| `load_interstitial_owned(ad_unit_id)` | `NativeHandle<Interstitial>` |
| `show_interstitial_owned(ad)` | `InterstitialOutcome` (`Dismissed`, `FailedToShow`) |
| `load_rewarded_owned(ad_unit_id)` | `NativeHandle<Rewarded>` |
| `show_rewarded_owned(ad)` | `RewardedOutcome { granted, reward_type, reward_amount }` |
| `show_banner_owned(BannerRequest { ad_unit_id, rect })` | `NativeHandle<Banner>` |
| `update_banner_owned(&banner, rect)` | `()` |
| `hide_banner_owned(banner)` | `()` |

Los métodos sin `_owned` (`load_interstitial`, `show_banner`, …) reciben
y devuelven `NativeHandleId`. `BannerRect` va en píxeles físicos;
`banner_rect_from_logical(x, y, w, h, scale)` hace la conversión.
`AdError` es `NotInitialized`, `NoFill`, `Network(String)`,
`InvalidRequest(String)`, `UnknownAd` o `Internal(String)`.

`BannerSlot` maneja un banner desde el código de UI: llama a
`sync(SlotTarget::Show(rect))` o `sync(SlotTarget::Hide)` en cada frame
y emite las llamadas de mostrar / actualizar / ocultar de una en una,
agrupando los cambios de rect. `status()`, `is_shown()` y `last_error()`
informan su estado; `with_spawn` ejecuta sus llamadas en tu executor en
vez de un hilo por llamada.

```rust
use std::sync::Arc;
use istmo::plugins::{BannerSlot, SlotTarget, banner_rect_from_logical};

let banner = BannerSlot::new("ca-app-pub-3940256099942544/9214589741", Arc::new(ads));
banner.sync(SlotTarget::Show(banner_rect_from_logical(0.0, 0.0, 320.0, 50.0, scale)));
```

### Resultados de actividades

`ActivityResultsClient::launch(IntentRequest) -> ActivityResult` lanza
una actividad de Android y espera su resultado. `IntentRequest { action,
uri, component, mime_type, categories, extras }`; `ActivityResult
{ outcome, data_uri, extras }` con `outcome` igual a `Ok`, `Cancelled` o
`Custom(i32)`; los extras son pares `(String, ExtraValue)` (`Text`,
`Int`, `Bool`, `Bytes`). Errores: `ActivityLaunchError`
(`NoActivityFound`, `NotAuthorized`, `Platform(String)`). Este contrato
no está en `istmo-plugins-schema`, así que el host nativo se escribe a
mano (`examples/android-demo` tiene uno).

### Tareas programadas

`TaskSchedulerClient` encola trabajo para un
[`#[istmo::worker]`](/istmo/es/writing-plugins/services-workers/):

- `enqueue(request: TaskRequest) -> TaskHandle`
- `cancel(handle: TaskHandle)`
- `cancel_by_tag(tag: String)`
- `cancel_by_unique_name(name: String)`

```rust
use istmo::plugins::{
    Constraints, ExistingWorkPolicy, NetworkKind, TaskRequest, TaskSchedulerClient,
};

let handle = TaskSchedulerClient::acquire()?
    .enqueue(TaskRequest {
        task_id: "myapp.sync".into(),
        unique_name: "nightly-sync".into(),
        input: Vec::new(),
        constraints: Constraints {
            required_network: NetworkKind::Unmetered,
            requires_charging: true,
            ..Constraints::default()
        },
        initial_delay_seconds: Some(3600),
        tags: vec!["sync".into()],
        existing_work_policy: ExistingWorkPolicy::Keep,
    })
    .await?;
```

`ExistingWorkPolicy` es `Replace` (por defecto), `Keep`, `Append` o
`AppendOrReplace`. Errores: `TaskSchedulerError` (`UnknownTask`,
`InvalidConstraints`, `Conflict`, `Platform`, cada uno con un `String`).

### Control de servicios

`ServiceControlClient` (`start_foreground`, `update_notification`,
`stop_foreground`, `acquire_wakelock`, `release_wakelock`, `stop_self`)
es lo que llama `ServiceContext` bajo `#[istmo::service]`; usa
`ctx.set_foreground(spec)`, `ctx.acquire_wakelock(tag)` y compañía en
vez del cliente. Ver
[Servicios y workers](/istmo/es/writing-plugins/services-workers/).
