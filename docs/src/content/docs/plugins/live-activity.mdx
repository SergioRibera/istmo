`istmo-live-activity` maps ActivityKit (iOS 16.2+) and Android ongoing
notifications behind a Rust trait. You describe your activity's
attributes and state in Rust; a native handler you write per activity
type renders them.

| Platform | Backend | Minimum |
| -------- | ------- | ------- |
| iOS | ActivityKit / Dynamic Island | 16.2 at runtime (the plugin builds for older releases, where it reports no support) |
| Android | ongoing notification: custom `RemoteViews`, `ProgressStyle` and Live Updates (both API 36) | API 26 |
| Desktop | — (every call fails) | — |

The Android minimum is declared in the plugin's `[min_versions]` and
checked at build time (see [istmo.toml
reference](/istmo/build-scripts/istmo-toml-reference/#min_versions)).

`capabilities()` reports no Dynamic Island flag on iOS: there is no public
API for it. The system shows your widget extension's Dynamic Island
layouts on devices that have one and the Lock Screen banner everywhere.

## Install

```toml
[dependencies]
istmo-live-activity = "0.1.1-alpha.5"
```

## Model your activity

Attributes are immutable per activity; state is updated over its
lifetime. Both are any `#[istmo::message]` type.

```rust
use istmo_live_activity::{ActivityStyle, DismissalPolicy, TypedLiveActivity};

#[istmo::message]
pub struct TimerAttributes {
    pub title:          String,
    pub target_seconds: u32,
}

#[istmo::message]
pub struct TimerState {
    pub elapsed_seconds: u32,
    pub label:           String,
}
```

`TypedLiveActivity<A, C>` pins the attribute and state types at compile
time and encodes them before they cross the wire; the native handler
registered for the activity type decodes them. Bind one adapter per
activity type:

```rust
let timers =
    TypedLiveActivity::<TimerAttributes, TimerState>::new(&runtime, "timer")?;

if !timers.are_activities_enabled().await? {
    return Ok(()); // or inspect timers.capabilities()
}

let handle = timers.start(
    TimerAttributes { title: "Focus block".into(), target_seconds: 25 * 60 },
    TimerState { elapsed_seconds: 0, label: "0:00 / 25:00".into() },
    ActivityStyle::Standard,
).await?;
```

`start_with_hint` also takes `stale_after_seconds` (iOS stale date) and
an `AndroidTierHint` (`ForceCustom`, `PreferSystemTemplates`,
`RequireLiveUpdate`). Methods return `ActivityError` directly.

## Update

```rust
timers.update(
    &handle,
    TimerState { elapsed_seconds: 60, label: "24:00 remaining".into() },
    None, // optional AlertConfig
).await?;
```

`handle` is a `NativeHandle<LiveActivityToken>`. **Dropping it ends the
activity** on both platforms. Keep it alive as long as the activity
should run. `update_by_id` / `end_by_id` take the raw `NativeHandleId`
for callers that keep the handle behind a lock.

## End

```rust
timers.end(
    &handle,
    Some(TimerState { elapsed_seconds: 25 * 60, label: "Done".into() }),
    DismissalPolicy::Default,
).await?;
```

`DismissalPolicy::Default` leaves the final state up for the platform's
default time, `Immediate` removes it right away and `AfterSeconds(n)`
holds it for `n` seconds. Dropping the handle after `end` is harmless.

## Restore after a restart

```rust
for restored in timers.restore().await? {
    // restored.handle, restored.attributes, restored.state
}
```

`restore` returns the activities of the adapter's type that are still
running, each under a handle the caller now owns. Handles this process
already owns are left out, so calling it again only returns activities
not seen before. An activity whose payload no longer decodes is skipped
with a warning and left running. The reference iOS handler restores
ActivityKit activities; the reference Android handler returns none.

## Native handlers

`LiveActivityBackendImpl` routes each call to the
`LiveActivityHandler` registered for its activity type; a type without
one fails with `ActivityError::UnknownActivityType`. The plugin ships
base classes under `plugins/live-activity/native/`:

- **iOS** — `ActivityKitLiveActivityHandler<Attributes: ActivityAttributes>`
  (iOS 16.2+). Subclass it, call `super.init(activityType:)` and
  override `decodeAttributes` / `decodeState` / `encodeAttributes` /
  `encodeState` to convert between the wire bytes and your Swift
  `ActivityAttributes`. The SwiftUI layouts (Lock Screen, Dynamic
  Island) go in a Widget extension with an `ActivityConfiguration`;
  the plugin does not generate them.
- **Android** — `NotificationLiveActivityHandler<A, C>(activityType, channel, context)`.
  Implement `renderStrategy()` (`RenderStrategy.CustomOnly`,
  `ProgressOnly` or `Adaptive`), `decodeAttributes`, `decodeState` and
  `smallIconRes`. `ChannelConfig.default()` creates the
  `istmo.live_activity` channel with `IMPORTANCE_LOW`.

To decode the payloads natively, pass your attribute and state types to
`istmo-build` as an extra contract (`AppOpts::extra_contracts`) so it
generates their Kotlin/Swift codecs —
[`examples/live-activity-demo`](https://github.com/SergioRibera/istmo/tree/main/examples/live-activity-demo)
does this in its `build.rs`.

## Wire it up

The backend needs your handlers, so turn off auto-registration for the
plugin in the app's `istmo.toml` and register the dispatcher yourself:

```toml
[[app.plugin]]
id = "istmo.live_activity"
auto_register = false
```

```kotlin
// Android: in your activity, after IstmoHost.onCreate(this)
val backend = LiveActivityBackendImpl(applicationContext).apply {
    register(TimerLiveActivityHandler(this@MainActivity))
}
IstmoRuntime.registerHandler(
    LiveActivityDispatcher.PLUGIN_ID,
    LiveActivityDispatcher(backend, LiveActivityCodecsImpl()),
)
```

```swift
// iOS: ios/<Name>App/main.swift
import IstmoRuntime

@_silgen_name("istmo_run_ios")
func istmo_run_ios() -> Int32

IstmoApp.run(
    registerPlugins: {
        IstmoPluginRegistry.registerAll()
        let backend = LiveActivityBackendImpl()
        if #available(iOS 16.2, *) {
            backend.register(handler: TimerLiveActivityHandler())
        }
        IstmoRuntime.shared.registerHandler(
            LiveActivityDispatcher.PLUGIN_ID,
            LiveActivityDispatcher(backend: backend, codecs: LiveActivityCodecsImpl())
        )
    },
    entry: istmo_run_ios
)
```

The plugin's Kotlin is generated into `dev.istmo.plugins.liveactivity`
(its `android_package`), next to the reference sources, whatever
`[app] android_package` your app uses. See
[Auto-registration](/istmo/build-scripts/auto-register/) for the
mechanism.

## Platform setup

- **iOS** — add `NSSupportsLiveActivities = true` to `Info.plist`
  (e.g. `[app.info_plist]` in the app's `istmo.toml`) and a Widget
  extension that renders your `ActivityAttributes`.
- **Android** — on Android 13+ the app needs the
  `POST_NOTIFICATIONS` permission, declared in its manifest and
  granted at runtime; without it `start` fails with
  `ActivityError::Disabled`.
