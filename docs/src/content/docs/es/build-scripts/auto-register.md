El auto-wiring del lado Rust recoge los **clients** de plugins
transparentemente vía `istmo::runtime!` (ver
[Auto-wiring](/istmo/es/advanced/auto-wiring/)). El lado nativo necesita su
propio mecanismo porque los **backends** de plugin —
`<T>BackendImpl.kt` / `<T>BackendImpl.swift` — son clases nativas que
el runtime tiene que construir.

`istmo-build` cierra el gap emitiendo un **`IstmoPluginRegistry`**
dentro de tu app, y el runtime trae entry points que lo llaman: el
equivalente al `GeneratedPluginRegistrant` + `FlutterActivity` de
Flutter.

## Entry points

### Android

Usa `IstmoGameActivity` (para UIs basadas en `GameActivity`, p. ej.
winit / eframe con `android-game-activity`) o `IstmoNativeActivity`
(`NativeActivity`, la feature default `native-activity` del facade)
como tu activity. El template la nombra directo en el manifest; haz
una subclase solo para añadir código Kotlin:

```xml
<activity android:name="dev.istmo.runtime.IstmoGameActivity" android:exported="true">
    <meta-data android:name="android.app.lib_name" android:value="my_app" />
    <!-- intent filter MAIN / LAUNCHER -->
</activity>
```

Antes de que corra el entry point de Rust, carga la librería que nombra
el meta-data `android.app.lib_name` de la activity, arranca
`IstmoRuntime` una vez por proceso y registra cada plugin con la activity
como host. Una app con su propia activity llama a `IstmoHost`:

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    IstmoHost.onCreate(this) // antes de super.onCreate
    super.onCreate(savedInstanceState)
}

override fun onDestroy() {
    super.onDestroy()
    IstmoHost.onDestroy(this)
}
```

### iOS

Para crates con un entry point `#[istmo::mobile_app]`, `istmo-build`
genera `Plugins/IstmoMain.swift`, y `main.swift` queda en una línea:

```swift
import IstmoRuntime

IstmoApp.run()
```

Arranca el runtime, llama a `IstmoPluginRegistry.registerAll()` y le
pasa el control a Rust. El entry point se detecta en las fuentes del
crate; setea `[app] rust_entry = true | false` para forzarlo. Las apps
con UI nativa llaman a `IstmoPluginRegistry.registerAll()` después de
`try IstmoRuntime.shared.start()`.

## Los archivos generados

El registry de Kotlin vive siempre en
`dev.istmo.generated.IstmoPluginRegistry`
(`android/app/src/main/java/dev/istmo/generated/`), así `IstmoHost` lo
encuentra sin configuración:

```kotlin
package dev.istmo.generated
// GENERATED by istmo-build - DO NOT EDIT.

object IstmoPluginRegistry : IstmoPluginRegistrant {
    private var shareBackend: Any? = null

    override fun registerAll(context: Context) {
        val appContext = context.applicationContext ?: context
        IstmoRuntime.registerHandler(
            dev.istmo.plugins.datastore.DataStoreDispatcher.PLUGIN_ID,
            dev.istmo.plugins.datastore.DataStoreDispatcher(
                dev.istmo.plugins.datastore.DataStoreFactoryImpl(appContext),
                dev.istmo.plugins.datastore.DataStoreCodecsImpl(),
            ),
        )
        if (context is Activity) {
            registerActivityPlugins(context)
        } else {
            Log.w(TAG, "activity-bound plugins skipped when registering from ${context.javaClass.name}")
        }
    }

    override fun registerActivityPlugins(activity: Activity) {
        hostActivity<androidx.activity.ComponentActivity>(activity, "istmo.share").let { host ->
            val current = shareBackend
            if (current is IstmoActivityBound) {
                current.attachActivity(host)
            } else {
                val backend = dev.istmo.plugins.share.ShareBackendImpl(host)
                shareBackend = backend
                IstmoRuntime.registerHandler(
                    dev.istmo.plugins.share.ShareDispatcher.PLUGIN_ID,
                    dev.istmo.plugins.share.ShareDispatcher(
                        backend,
                        dev.istmo.plugins.share.ShareCodecsImpl(),
                    ),
                )
            }
        }
    }

    override fun releaseActivityPlugins() {
        if (shareBackend !is IstmoActivityBound) {
            IstmoRuntime.unregisterHandler(dev.istmo.plugins.share.ShareDispatcher.PLUGIN_ID)
            shareBackend = null
        }
    }
    // …
}
```

El espejo de iOS vive en `ios/<AppDir>/Plugins/IstmoPluginRegistry.swift`.
Ambos se regeneran en cada build (y se emiten aunque estén vacíos);
agrégalos al `.gitignore`.

## Qué significa "elegible"

Un plugin aparece en el registry cuando se cumple **todo** esto:

- El rol del plugin es `host` (el lado nativo implementa el backend).
  Los plugins con rol `client` no registran dispatcher: generan un
  `<T>Client` para que lo llame el lado nativo.
- El `istmo.toml` del plugin tiene `auto_register = true` (default).
- El `istmo.toml` de la app no lo pisa con `auto_register = false`
  para ese plugin.
- `[app] auto_register` no es `false`.
- El contrato tiene algo que despachar: un contrato que sólo lleva
  tipos (sin métodos ni `init`) no tiene backend y queda fuera.
- Existe una clase de backend nativa **en esa plataforma** (se evalúa
  por plataforma, así que un plugin puede registrarse en Android y no
  en iOS). Alguna de estas:
  - el crate del plugin trae fuentes `native/android/` (Android) o
    `native/ios/` (iOS);
  - el `istmo.toml` del plugin declara `android_backend` /
    `ios_backend`;
  - la app genera el backend con `AppOpts::seed_backends` (en Android
    sólo para contratos sin `android_package` de plugin);
  - la app lo pide explícitamente con `[[app.plugin]] auto_register =
    true`: así se registra un contrato local de la app cuyo
    `<T>BackendImpl` escribe la propia app.

  Un plugin alojado en Rust no cumple ninguna, así que queda fuera del
  registry sin necesidad de `auto_register = false`.

`auto_register = false` (en el plugin, en `[[app.plugin]]` o en `[app]`)
siempre gana sobre la última regla.

## Construcción

- **Plugins stateless**: `<T>Dispatcher(<backend>, <T>CodecsImpl())`.
- **Plugins stateful** (trait declarado con `init = Config`): la clase
  es una factory que materializa un backend por instancia.

El `istmo.toml` del plugin dice qué clase y qué recibe:

```toml
[plugin]
id                  = "istmo.share"
android_backend     = "dev.istmo.plugins.share.ShareBackendImpl"
android_backend_arg = "activity"
ios_backend         = "ShareBackendImpl"
```

- **`android_backend`**: clase Kotlin completamente calificada. Default:
  `<T>BackendImpl` / `<T>FactoryImpl` en el `android_package` del plugin,
  o si no en el package de codegen de la app.
- **`android_backend_arg`**: `"context"` (default), `"activity"`
  (`androidx.activity.ComponentActivity`) o una subclase de `Activity`
  completamente calificada, como `"androidx.fragment.app.FragmentActivity"`.
  Los plugins atados a una activity se saltean (con un log) cuando el
  registry corre sin activity (p. ej. desde un `Service`), y fallan con
  un error claro cuando la activity host no es del tipo requerido. Los
  handlers son de todo el proceso, así que los backends `"context"`
  reciben el application context; los atados a una activity siguen a
  la activity viva creada más recientemente. Un backend que implementa
  `dev.istmo.runtime.IstmoActivityBound` se construye una sola vez por
  proceso, guarda la activity con una referencia débil y recibe cada
  activity nueva por `attachActivity`, así su estado sobrevive a la
  recreación. Cualquier otro backend atado a una activity se reconstruye
  en cada `onCreate` (necesario si registra launchers de activity
  result) y se desregistra cuando se destruye la última activity, así
  una activity terminada nunca queda alcanzable desde el runtime.
  `IstmoHost.currentActivity()` devuelve la activity host actual para
  el código que la busca en el momento.
- **`ios_backend`**: tipo Swift, construido sin argumentos. Default:
  `<T>BackendImpl` / `<T>FactoryImpl`.

## Opt-out

### Por plugin (autor del plugin)

Para backends cuya construcción varía por app (una API key, una view de
la app):

```toml
[plugin]
id            = "acme.push_notifications"
client_type   = "::acme_push::PushClient"
auto_register = false
```

### Por plugin (autor de la app)

```toml
[[app.plugin]]
id            = "istmo.data_store"
auto_register = false
```

El registry omite el plugin; regístralo tú después de
`IstmoHost.onCreate(this)` (Android) o dentro de
`IstmoApp.run(registerPlugins:entry:)` (iOS).

### Globalmente

```toml
[app]
auto_register = false
```

Los registries se siguen generando, vacíos.

## Debugging

Si al registry le falta un plugin que esperabas:

- Confirma que el `istmo.toml` del plugin no tenga `auto_register = false`.
- Confirma que no tengas un override `[[app.plugin]]` que matchee en tu
  app.
- Confirma que no estés usando `role = "client"` para ese plugin.
- Confirma que exista un backend para esa plataforma: el crate del
  plugin trae `native/<plataforma>/` o declara `android_backend` /
  `ios_backend`. Para un contrato local de la app, agrega
  `[[app.plugin]] id = "…"` con `auto_register = true`.
