# High-rate data without the bus

Design for moving high-rate data (stream items, video frames, audio
buffers) between an istmo plugin and its consumer without paying the
frame protocol's encode / route / decode cost per item. Covers:

- **(a)** the typed in-process shortcut, installed by every host
  registration, for unary and `#[stream]` methods,
- **(b)** native frame sinks: a typed, per-session channel for buffers
  that must never be serialised (DMA-BUF, `AHardwareBuffer`,
  `CVPixelBuffer` / `IOSurface` / `CMSampleBuffer`, D3D11 textures,
  shared CPU memory),
- **(c)** the Android / iOS producer sessions that hand native buffers
  to Rust directly, generated by `istmo-build` like the rest of the
  bridge,
- **(d)** who may feed a sink, and what happens across the bus,
- **(e)** how existing plugins benefit (camera).

Status: (a)–(d) implemented in `istmo-core`, `istmo-macros`,
`istmo-build`, `istmo-android`, `istmo-ios` and the Kotlin / Swift
runtimes, host-tested (Linux), Miri-clean on the pure-Rust parts.
Android and iOS entries are compile- and parity-checked, not yet run on a
device. Camera migration (e) is described, not done.

## Why

What a plugin pays per stream item on the wire:

| Path | Per item |
|---|---|
| Rust host → Rust client (same runtime) | encoder thread receives `T`, `codec::encode` into a fresh `Vec<u8>`, flume hop to the pump, routing-table lookup, flume hop to the `StreamHandle`, `codec::decode` into a fresh `T` |
| Kotlin / Swift host → Rust client | native encode into `ByteArray` / `Data`, JNI / FFI copy into `Vec<u8>`, `Frame::Event` dispatch, routing, decode |

For a 1080p NV12 frame (3 MB) that is three to four full copies plus
two allocations per frame, before the consumer touches a pixel.
ferricast rejected istmo streams for its codec data plane for exactly
this reason, and every media plugin so far (camera, webview
presentation) grew its own out-of-band path. The webview's `FrameSink`
registry (`plugins/webview/src/present.rs`) is the in-process precedent
this design generalises.

Non-goals:

- No new wire frames: `PROTOCOL_VERSION` stays 4.
- No cross-process buffer sharing (yet): see (d).
- No GPU API in istmo. istmo moves ownership of a buffer; importing it
  into Vulkan / Metal / D3D is the consumer's business.

## (a) Typed in-process shortcut

`#[istmo::plugin]` emits `<Trait>Typed` for stateless plugins and
implements it on `<Trait>Host` by delegation. The host's
`Dispatch::typed_shortcut` hands it to the runtime, and
`Runtime::register_host` / `register_host_arc` — so every
`runtime!(hosts: …)` entry and `RuntimeInit::host` — install it next to
the wire dispatcher. The generated client checks the slot (one atomic
load when no typed host exists, then one map lookup) and calls through
it: no encode, no routing, no dispatcher thread. `client.is_local()`
reports whether it does.

| Method | Typed path |
|---|---|
| unary `async fn` | the host future, boxed, polled on the caller's task inside `catch_unwind` (a panic is `PluginError("host panicked")`, as on the wire) |
| unary taking a `CancelToken` | `typed_call_cancellable`: the call is tracked like a hosted call (shutdown trips its token); dropping it before it finished trips the token and hands the host future (it owns an `Arc` of the host) to a thread of its own that runs it to the end — so a host's cleanup after a cancel runs exactly as it does under the dispatcher |
| `#[stream]` | the implementation is called on the caller's thread and its own `flume::Receiver` becomes the `TypedStream` (`open_local{,_fallible}`); no encoder thread, no pump |
| `#[istmo::blocking]` | not in `<Trait>Typed`: the client takes the wire path, the call runs on a dispatcher thread |
| methods taking `HostCtx` | the client passes `HostCtx::new(rt, CallOrigin::Local)` |

`TypedStream<Item, Err>` keeps its public shape. A local stream ends as
`Completed` when the producer drops its sender, `Cancelled` when its
token tripped (a producer that obeys the cancel by dropping the sender
also yields `Cancelled`), `Failed(e)` at the first `Err`.

### Opt-outs

- `#[istmo::blocking]` on a method: blocks a thread (synchronous dialog,
  large `std::fs`, sleeps), hops to the main thread and waits, or only
  runs on a particular executor (one that needs a tokio reactor).
- `#[plugin(shortcut = false)]`: no `<Trait>Typed` at all.
- `runtime!(hosts: [#[wire_only] T => impl])` /
  `Runtime::register_host_wire_only`: one registration stays on the wire.

Stateful (`init = …`) plugins keep the wire path; an instance-keyed slot
is a follow-up. Calls from Kotlin, Swift and other processes always take
the wire path.

### Audit of existing hosts (before enabling it by default)

Every Rust implementation of a stateless plugin trait in `plugins/*`,
`crates/plugins`, the examples, tests and benches was checked for
blocking calls, executor dependence, synchronous main-thread hops and
synchronous runtime re-entry. None depends on a specific executor
(zbus runs on `async-io`, WinRT futures are executor-agnostic). Marked
`#[istmo::blocking]`:

| Plugin | Method | Why |
|---|---|---|
| file-picker | `pick_file`, `pick_files`, `save_file` | synchronous `rfd` dialogs (a modal loop on macOS, an STA COM dialog on Windows) |
| web-auth | `authenticate` | a sleep-poll loop for the whole browser round trip |
| share | `share` | payload staging with blocking `std::fs`; on Windows, `RoInitialize(MTA)` on the calling thread |
| share | `capabilities` | `RoInitialize` on the calling thread for packaged Windows apps |
| dnd | `start_drag` | macOS starts the drag with a synchronous hop to the main thread |

Left on the shortcut: biometric (async zbus, WinRT futures; the macOS
keychain reads `has_secret` / `delete_secret` / `enrollment_state` are
short synchronous XPC calls), opener (`Command::spawn`, the wait runs on
its own thread), barcode-scanner, live-activity, the `crates/plugins`
`Unavailable*` hosts, every example and test host. The biometric fprintd
test that drops an `authenticate` call mid-scan passes unchanged on the
shortcut: the abandoned future finishes `VerifyStop` / `Release` on its
own thread.

### Rejected

- Keeping the shortcut opt-in: the user decision is "fast by default";
  the method marker covers the hosts that cannot run on the caller.
- Running every typed method on a spawned thread: re-adds the thread the
  shortcut removes.
- A separate `local_*()` client method: callers should not choose the
  path; the runtime knows where the host is.

## (b) Native frame sinks

A frame sink is a per-session, typed, bounded mailbox owned by the
consumer and fed by producers that may be Rust (a desktop backend), a
Kotlin backend or a Swift backend. Each item is a `NativeFrame<M>`:
plugin-defined metadata `M` plus a `NativeBuffer` whose drop releases
the memory to whoever produced it.

### Types (`istmo_core::native_frame`, re-exported at the crate root)

```rust
pub struct FrameSinkId<M>  { /* random u64 + PhantomData<fn() -> M> */ } // Copy, wire = u64
pub struct FrameSink<M>    { /* consumer end; Stream<Item = NativeFrame<M>> */ }
pub struct FrameSender<M>  { /* producer end; every clone is one producer */ }
pub struct NativeProducer  { /* native producer session, see (c) */ }
pub struct NativeFrame<M>  { pub meta: M, pub buffer: NativeBuffer, /* seq, dropped_before */ }
pub struct NativeBuffer    { /* Arc<holder: backing + hooks + identity> */ }
pub struct SinkPolicy      { /* depth: NonZeroUsize, overflow */ }  // latest(), queue(usize)
#[non_exhaustive] pub enum Overflow { DropOldest, DropNewest }
#[non_exhaustive] pub enum EndReason { Completed, ProducerGone, Failed(SinkError), ConsumerClosed, Shutdown }
#[non_exhaustive] pub struct SinkStats { accepted, delivered, evicted, refused, discarded }
#[non_exhaustive] pub enum MemoryKind { Cpu, DmaBuf, HardwareBuffer, CvPixelBuffer, IoSurface, CmSampleBuffer, D3d11Texture, VideoFrame, Other }
pub struct BufferIdentity  { pub pool_generation: u64, pub slot: u32 }
pub trait  PlatformBuffer  { fn kind(&self) -> MemoryKind; fn as_ptr(&self) -> NonNull<c_void>; }
```

Consumer: `rt.open_frame_sink::<M>(policy)`, hand `sink.id()` to the
producer, then `recv` / `recv_async` / `try_recv` or the `Stream` impl;
`None` once ended and drained, `end_reason()` then says why. Rust
producer: `ctx.frame_sender(id)` (`HostCtx`) or `rt.frame_sender(id)`,
then `push`, `close`, `close_with(error)`.

### Ids and registry

Ids come from a SipHash of a counter keyed by a per-runtime
`RandomState`: unguessable, and unique across runtimes (an id from
another runtime resolves to nothing). The registry maps id → type-erased
sink; it is touched when a sink opens or closes and when a producer
resolves, never per frame. The 256 most recently closed ids are
remembered (also at shutdown), so a late producer hears `Closed` rather
than `UnknownSink`.

### Producers and ends

Every producer handle — each `FrameSender` resolution and clone, each
native producer session — counts once. The last one to go ends the sink
as `ProducerGone`; resolving an id again (a check, a second producer)
never ends a live stream. `close()` ends it as `Completed`,
`close_with(error)` / a native `closeWithError` as `Failed`. The
consumer ends it by `close()` (queued frames stay receivable) or by
dropping it (queued frames are released, counted `discarded`); shutdown
ends every sink as `Shutdown`.

### Waking receivers

The sink keeps the wakers of waiting receivers next to its queue (the
first inline, more in a `Vec`); a push or an end takes them under the
lock and wakes them all after it. Blocking `recv` parks on a cached
per-thread waker, so it neither allocates nor registers twice. Every
waiter wakes on each frame and at the end: two receivers can never leave
one asleep with a frame queued or after the end. A push to a busy
consumer (nobody waiting) wakes nobody.

### Ownership, leases, release

- A `NativeBuffer` is one `Arc` allocation holding the backing, a view
  (`as_bytes`, `platform_ptr`), an optional `BufferIdentity` and the
  release hooks (the first inline). The backing's `Drop` releases what it
  owns; hooks run after it. Each runs under `catch_unwind`: a panicking
  release is logged, the others still run, and nothing unwinds into a
  producer (eviction), a consumer, or a JNI / C entry.
- `Clone` shares; release fires once, when the last clone drops, on
  that thread.
- `into_backing::<B>()` moves the backing out with a `BufferLease`
  (`Send + Sync`) holding the hooks; `IntoBackingError::{Shared,
  WrongType}` gives the buffer back.
- Platform objects use `NativeBuffer::from_platform(P: PlatformBuffer)`
  and are read uniformly with `platform_ptr()` + `kind()`, whoever made
  them: `istmo_android::HardwareBuffer`, `istmo_ios::RetainedBuffer`, a
  plugin's D3D11 texture.
- DMA-BUF: `from_dmabuf(impl Into<Arc<DmaBuf>>)`; planes carry `fd`,
  `offset`, `stride` and the object `size` (Vulkan / EGL imports need
  it). A pooled producer keeps an `Arc<DmaBuf>` per slot and pushes
  clones — no `dup` per frame, stable fd numbers — and tags frames with
  `BufferIdentity` so consumers cache imports per slot. Debug builds
  assert plane fds are close-on-exec. A PipeWire producer requeues a
  buffer from its loop thread: its release hook posts to the loop.
- **Synchronisation contract**: no fence travels with a frame. The
  producer pushes only finished frames (it waits, bounded, on its acquire
  fence: implicit sync, a syncobj point, `Image.getFence()`), and
  dropping the buffer or its lease means every consumer read, GPU work
  included, is complete; the producer signals its release point from the
  release hook. The `FrameSync::Timeline` variant the screen-capture
  draft carried is removed from the data plane.

### Backpressure

Producers never block:

| Policy | Full sink | Use |
|---|---|---|
| `latest()` | replace the queued frame (`DropOldest`) | previews, mirroring |
| `queue(n)` (`n ≥ 1`, panics on 0) | evict the oldest | encoders tolerating a hiccup |
| `queue(n).with_overflow(DropNewest)` | refuse the new frame, give it back | contiguous prefixes (audio) |

`evicted` (accepted, then lost; reported as `dropped_before()` on the
next frame) and `refused` (handed back; a retrying producer counts each
attempt) are separate counters. Evicted frames are released outside the
sink's lock. A blocking policy was rejected: it would stall capture
callbacks that must return quickly.

## (c) Native producer sessions

No per-plugin trampolines: the transports export one fixed set of
entries, and a producer session resolves the sink once.

`Runtime::open_native_producer(sink, fingerprint) ->
Result<NativeProducer, SubmitStatus>` checks the sink exists (`Closed`
for a recently closed one, `UnknownSink` otherwise) and that
`fingerprint` — FNV-1a 64 of the metadata type's path-less Rust name
(`meta_fingerprint::<M>()`; `istmo-build` computes the same from the
contract, a test pins them equal) — matches (`TypeMismatch`). The
session holds the sink directly: a submit decodes the metadata from a
borrowed slice and pushes, with no registry lock and no
`Runtime::global()`. It counts as one producer until dropped.

`SubmitStatus` (also `IstmoSubmitStatus` in Kotlin and Swift, C
constants `ISTMO_SUBMIT_*`; a parity test checks all four): `ACCEPTED 0`,
`DISPLACED 1`, `CLOSED 2`, `UNKNOWN_SINK 3`, `BAD_META 4` (logged once
per sink), `UNSUPPORTED 5`, `NOT_STARTED 6`, `INVALID 7`, `FULL 8`,
`INTERNAL 9` (Rust failed after taking the buffer; Rust releases it),
`TYPE_MISMATCH 10`. `is_taken()` / `isTaken`, `should_stop()` /
`shouldStop`.

`NATIVE_ABI_VERSION` (1) is exported as `IstmoFrames.nativeAbiVersion`
/ `istmo_abi_version`; `IstmoRuntime.start` refuses a library reporting
another version (or none: a pre-version library is an
`UnsatisfiedLinkError` turned into a readable error).

### Android

`istmo-android::frame_exports`, bound by the Kotlin object
`dev.istmo.runtime.IstmoFrames` (`Java_dev_istmo_runtime_IstmoFrames_*`):

| `external fun` | Rust |
|---|---|
| `nativeOpenProducer(sink, fingerprint, status: IntArray): Long` | boxes an `AndroidProducer` (the `NativeProducer`, a release queue, an optional slot pool) and returns its address; 0 with the status otherwise |
| `nativeEndProducer(handle, error: String?)` / `nativeFreeProducer(handle)` | end the stream / drop the session |
| `nativeSubmitHardwareBuffer(handle, buffer, ticket, meta, metaLen)` | `AHardwareBuffer_acquire` (own reference, `dlsym`ed: API 26+), and a release hook that pushes `ticket` onto the release queue |
| `nativeOpenSlotPool(handle, slotSize, count)` → `ByteBuffer[]`, `nativeAcquireSlot`, `nativeReleaseSlot`, `nativeSubmitSlot(handle, slot, length, meta, metaLen)` | Rust-owned slots exposed once with `NewDirectByteBuffer`; a submitted slot is a frame's until it drops, then free for `acquire` again (`u64` free / held masks) |
| `nativeSubmitBytes`, `nativeSubmitDirectBuffer` | copy |
| `nativeAwaitReleased(handle, timeoutMs): LongArray` | released tickets, waiting on a condvar |

Release model: **Rust never holds a JNI reference.** A frame that came
from an `Image` keeps the `Image` open in Kotlin (`owners[ticket]`);
whichever thread drops the frame only pushes the ticket (a mutex and a
condvar, no JNI, no thread attach). The sender's daemon releaser thread
— already attached, it is a Java thread — waits in
`nativeAwaitReleased` and closes the owners, so the `ImageReader`'s
producer never renders into a buffer a consumer still reads. Every
ticket handed to Rust comes back, refused or not; a ticket Rust never
saw is closed by Kotlin. CPU bytes are either Rust-owned slots (the
memory Rust reads is never freed or rewritten by the JVM) or copied: the
old zero-copy view of a caller's direct `ByteBuffer` (whose owner could
free or rewrite it) is gone.

Kotlin `IstmoFrameSender<M>`: opened by the generated dispatcher
(`IstmoFrameSender.open`, behind the `@IstmoGeneratedApi` opt-in), one
producer session, `AutoCloseable` (and a finalizer as a safety net).
Submits are serialised on the sender; the metadata is written into a
reused buffer and passed with its length (no `toByteArray`), read in
Rust onto the stack. `submit(Image, meta)` needs API 28
(`getHardwareBuffer`) and waits up to 1 s on `Image.getFence()` on API
33+; `submit(HardwareBuffer, meta, owner)` API 26, checking `isClosed`
first. Supported `ImageReader` combinations (the platform's rule):
non-`PRIVATE` formats with `CPU_READ_*`, `PRIVATE` with
`GPU_SAMPLED_IMAGE` / `VIDEO_ENCODE`; size `maxImages` for the frames a
consumer holds plus one.

### iOS

`istmo-ios` exports, declared in `istmo_ffi.h` (a test checks every
signature both ways):

```c
uint32_t istmo_abi_version(void);
IstmoFrameProducer * istmo_ios_open_frame_producer(uint64_t sink, uint64_t fingerprint, int32_t *status);
void istmo_ios_end_frame_producer(const IstmoFrameProducer *p, const uint8_t *error, size_t error_len);
void istmo_ios_free_frame_producer(IstmoFrameProducer *p);
int32_t istmo_ios_submit_native_buffer(const IstmoFrameProducer *p, uint32_t kind,
    void *object, IstmoReleaseFn release, const uint8_t *meta, size_t meta_len);
int32_t istmo_ios_submit_frame_bytes(const IstmoFrameProducer *p,
    const uint8_t *bytes, size_t len, const uint8_t *meta, size_t meta_len);
```

Swift passes `Unmanaged.passRetained(object).toOpaque()` and a
`@convention(c)` release; Rust owns that +1 and releases it exactly once
(on drop, or at once when refused). A retained `CVPixelBuffer` is not
recycled by its pool while Rust holds it. Metadata is read in place.
Swift `IstmoFrameSender<M>` is a `final class`, `@unchecked Sendable`
behind an `NSLock`, freed in `deinit`; generated message types are
`Sendable`. Conveniences for `CVPixelBuffer`, `IOSurfaceRef` and
`CMSampleBuffer` live behind `canImport`.

### Generated surface

`sink: FrameSinkId<M>` (or `Option<FrameSinkId<M>>`) in a method's
arguments becomes `TypeRef::FrameSink(M)` (handover tag 17; the handover
payload starts with `CONTRACTS_FORMAT` = 2, and an unreadable one fails
the build). Kotlin and Swift backends receive `IstmoFrameSender<M>`
(`?` for an optional one); generated Kotlin and Swift **clients** omit
methods taking sinks (they cannot open one). Rust needs nothing
generated.

## (d) Who may feed a sink

| Situation | Result |
|---|---|
| Rust consumer, Rust host, same runtime | zero-copy push |
| Rust consumer, Kotlin / Swift host, same process | native producer session |
| A call carrying a sink from Kotlin, Swift or another process to a Rust host | `DispatchError::OriginRefused` (generated hosts check `CallOrigin::Local`) |
| A Rust client sending a sink to a plugin declared remote | `IstmoError::FrameSinkNotShareable` before anything is sent |
| An id from another runtime | `UnknownFrameSink` / `UNKNOWN_SINK` |

Plugins that want remote consumers expose an explicit CPU path (a
`#[stream]` of encoded frames). Future work, when a consumer needs it:
`HardwareBuffer` (Parcelable) and DMA-BUF fds (`SCM_RIGHTS`) through the
remote bridge.

App code hands platform objects to plugins as `NativeHandleId`s:
`IstmoRuntime.registerObject(surface)` (Kotlin) /
`IstmoRuntime.shared.registerObject(layer)` (Swift) returns an id the
app passes as a plugin argument (a preview `Surface`, a consent grant);
the backend reads it with `objectFor<T>(id)` / `object(for:)`; it is
released when Rust drops its `NativeHandle` or with `releaseObject`.

## (e) Existing plugins

**Camera** copies every frame today (`CameraFrame { bytes }` built in
Kotlin / Swift, encoded, decoded, fanned out by cloning). Migration:
`open_frames(session, sink: FrameSinkId<FrameInfo>)`; Android
`frames.submit(image, info)` (the `Image` stays open until released);
iOS `frames.submit(sampleBuffer, info)`; desktop (nokhwa)
`NativeBuffer::from_bytes(frame_bytes)`. Camera is stateful, so it
benefits from (b), not (a), until the shortcut learns instances.

**Webview** keeps its own latest-value slot. **ferricast's codec
plugin** can move its data plane onto sinks.

**Web**: a `VideoFrame` is a JS object bound to its thread while buffers
are `Send`, so web producers copy (`VideoFrame.copyTo` into a
`from_bytes` backing) until a thread-bound backing exists;
`MemoryKind::VideoFrame` names it.

## Measurements

Release build, AMD Ryzen 9 9950X3D, Linux 6.18. Criterion
(`crates/core/benches/stream_paths.rs`) plus a counting-allocator
harness for allocations and contention. The workloads are plain
functions of a runtime, so the same rows can run on Android / iOS
devices later.

Pipelined, per item:

| Path | 16 B | 8 MiB |
|---|---|---|
| bus stream | 328 ns | 1 037 µs |
| typed stream shortcut | 350 ns | 76 µs |
| frame sink, Rust producer | 375 ns (329 before) | 61 µs |
| frame sink, native producer session | 425 ns (488 before, raw-id submit) | 61 µs |
| frame sink, pool of 4 recycled by a release hook | | 18 µs |

The 16 B sink row lost ~45 ns to waking every waiter (correctness for
several receivers); at that size every path is bound by the thread
hand-off, and sinks are not meant for items a stream carries as well.
Single-thread criterion hand-off: flume 23 ns, encode + channel +
decode 43 ns, sink push + `try_recv` 47 ns, native session submit 49 ns
(64 ns before).

Single thread, one frame handed over and taken back (allocations per
frame):

| Path | before | after |
|---|---|---|
| push + `try_recv` | 53 ns, 2 | 58 ns, 2 |
| push with a release hook | 70 ns, 3 | 64 ns, 2 |
| native submit (meta decoded) + `try_recv` | 73 ns, 2 | 61 ns, 2 |
| iOS submit (meta copied → borrowed), 69-byte meta | 149 ns, 6 | 125 ns, 5 |
| parked consumer woken (`recv`), allocations per item | 3 | 2 |
| pooled DMA-BUF, `Arc<DmaBuf>` clone instead of `dup` per plane | 137 ns, 2 | 41 ns, 1 |

Native submits, each thread on its own sink:

| Threads | registry lock per frame (before) | producer session (after) | Rust `FrameSender` |
|---|---|---|---|
| 1 | 66 ns | 50 ns | 50 ns |
| 4 | 468 ns | 139 ns | 101 ns |
| 16 | 2 711 ns | 300 ns | 300 ns |
| 32 | 5 235 ns | 506 ns | 471 ns |

What remains at high thread counts is the allocator, not istmo.

## Open questions

1. Stateful typed shortcut (instance-keyed slots) — camera needs it for (a).
2. Cross-process buffers (Binder `HardwareBuffer`, `SCM_RIGHTS` DMA-BUF,
   XPC `IOSurface`).
3. A thread-bound buffer for the web's `VideoFrame`.
4. Rust ↔ mobile latency, measured on devices with the same workloads.
