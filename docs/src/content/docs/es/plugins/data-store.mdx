`istmo-data-store` es un store key/value native-hosted. La API Rust es
idéntica en cada plataforma; el backend usa `SharedPreferences` en
Android, `UserDefaults` en iOS y un archivo por namespace en desktop.
Los backends móviles viajan en el crate del plugin bajo
`native/{android,ios}/` con cero deps externas.

## Instala

```toml
[dependencies]
istmo-data-store = "0.1.1-alpha.5"
```

## Úsalo

`DataStore` es stateful (`init = DataStoreConfig`) — la config lleva
el namespace bajo el que el backend segrega valores. Un namespace es
un nombre corto para un grupo de valores dentro de la app
(`"settings"`, `"session"`); las plataformas ya separan unas apps de
otras, así que no necesita el id de la app. En Android forma parte de
un nombre de archivo y no puede contener `/`.

```rust
use istmo_data_store::{DataStoreClient, DataStoreConfig};

let store = DataStoreClient::from_runtime_with(&runtime, DataStoreConfig::new("settings")).await?;
// …o sobre el runtime global del proceso:
// let store = DataStoreClient::acquire_with(DataStoreConfig::new("settings")).await?;

store.set_string("user.email".into(), "iris@example.com".into()).await?;
store.set_bool("onboarding.completed".into(), true).await?;
store.set_i64("last_sync_ms".into(), now_ms()).await?;

let email = store.get_string("user.email".into()).await?;
let done  = store.get_bool("onboarding.completed".into()).await?;
```

Cada getter retorna `Option<T>` — keys faltantes son `None`, no un
error. `set_f64` / `get_f64` cubren floats y `set_bytes` / `get_bytes`
cubren `Vec<u8>` para blobs opacos.

Leer una key con un tipo distinto al que se escribió falla con
`DataStoreError::Corrupted` en todas las plataformas. Los errores de
dominio llegan como `IstmoError::PluginError { bytes }`; decodéalos con
`istmo::codec::decode::<DataStoreError>(&bytes)`.

### Eliminar y listar

```rust
store.remove("user.email".into()).await?;   // retorna bool: ¿estaba presente?
store.clear().await?;                       // borra el namespace
let all_keys = store.keys().await?;         // Vec<String>
let has_key  = store.contains("theme".into()).await?;
```

## Storage subyacente

| Plataforma | Backend | Ubicación |
| ---------- | ------- | --------- |
| Android | `SharedPreferences` | archivo `<package name>.istmo.<namespace>` en el data dir de la app |
| iOS | `UserDefaults` | suite `<bundle id>.istmo.<namespace>` |
| Windows | `DesktopDataStore` | `%APPDATA%\<bundle-id>\config\data-store\<namespace>.bin` |
| macOS | `DesktopDataStore` | `~/Library/Preferences/<bundle-id>/data-store/<namespace>.bin` |
| Linux | `DesktopDataStore` | `$XDG_CONFIG_HOME/<bundle-id>/data-store/<namespace>.bin` (por defecto `~/.config/…`) |

El namespace nunca se usa solo como nombre de archivo o de suite, así
que no puede chocar con las preferencias propias de la app. En desktop
se codifica con percent-encoding (mayúsculas incluidas), así que
namespaces distintos van a archivos distintos también en sistemas de
archivos case-insensitive, y un archivo que ya no decodifica se mueve
a `<file>.corrupt` y el namespace arranca vacío. El `<bundle-id>` de
desktop sale de `ISTMO_APP_BUNDLE_ID` (lo fija `istmo-build`), con el
nombre del crate como fallback.

Todos los backends son **solo key/value** — sin queries, sin
encriptación. No lo uses para secretos (ver
[Biometric](/istmo/es/plugins/biometric/) para secretos ligados a
biometría); úsalo para preferencias de usuario y cache low-security.

## Cablealo

Los entry points del runtime llaman una sola vez al
`IstmoPluginRegistry` generado — esa llamada cablea todos los
dispatchers de plugins elegibles, incluyendo este. Las apps creadas
con el template no necesitan nada extra.

### Android

```kotlin
// IstmoGameActivity, la launcher del template, ya hace esto.
// Una app con su propia activity llama a IstmoHost antes de super.onCreate:
override fun onCreate(savedInstanceState: Bundle?) {
    IstmoHost.onCreate(this) // arranca el runtime + IstmoPluginRegistry
    super.onCreate(savedInstanceState)
}
```

### iOS

```swift
// ios/<Name>App/main.swift
import IstmoRuntime

IstmoApp.run() // arranca el runtime + IstmoPluginRegistry, luego corre Rust
```

Los archivos `DataStoreBackendImpl` / `DataStoreFactoryImpl` de
referencia viven en `plugins/data-store/native/{android,ios}/`
(paquete Kotlin `dev.istmo.plugins.datastore`, que es también donde
`istmo-build` genera el Kotlin del plugin, sea cual sea el
`[app] android_package` de tu app). El plugin de Gradle y el fragmento
xcodegen `istmo-plugins.yml` los compilan dentro de la app; no hay
nada que copiar.

Ver [Auto-registración](/istmo/es/build-scripts/auto-register/) para
detalles de cómo se genera el registry y cómo opt-out.

### Desktop

Las apps desktop hospedan el plugin en Rust. Registra el host stateful
una vez; cada `DataStoreConfig` abre luego un `DesktopDataStore`:

```rust
use istmo_data_store::{DataStoreHost, DesktopDataStoreFactory};

runtime.register_host(DataStoreHost::new(DesktopDataStoreFactory));
```

Las instancias abiertas para el mismo namespace en un proceso
comparten un único mapa en memoria; procesos distintos que escriben el
mismo namespace no se coordinan.

## Ejemplo

[`examples/data-store-demo`](https://github.com/SergioRibera/istmo/tree/main/examples/data-store-demo)
es un solo crate que produce un binario desktop (con
`DesktopDataStoreFactory` hospedado en el proceso) y la app Android /
iOS a partir de la misma UI egui.

## Threading

Todo es `suspend` en Kotlin y `async` en Swift; los backends de
referencia usan el dispatcher default / cualquier thread. Si
reemplazas el backend por algo con threading más estricto, gatéalo
apropiadamente.

## No incluido (por ahora)

- Encriptación. Envuelve el plugin detrás de tu propio trait si la
  necesitas.
- Suscripción a cambios. No hay un stream de cambios sobre un
  namespace.
