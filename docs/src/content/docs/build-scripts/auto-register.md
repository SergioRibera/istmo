Rust-side auto-wiring picks up plugin **clients** transparently through
`istmo::runtime!` (see [Auto-wiring](/istmo/advanced/auto-wiring/)). The
native side needs its own mechanism because the plugin **backends** —
`<T>BackendImpl.kt` / `<T>BackendImpl.swift` — are native classes the
runtime has to construct.

`istmo-build` closes the gap by emitting an **`IstmoPluginRegistry`**
into your app, and the runtime ships entry points that call it — the
equivalent of Flutter's `GeneratedPluginRegistrant` + `FlutterActivity`.

## Entry points

### Android

Use `IstmoGameActivity` (for `GameActivity`-based UIs, e.g. winit /
eframe with `android-game-activity`) or `IstmoNativeActivity`
(`NativeActivity`) as your activity — directly in the manifest or as an
empty subclass:

```kotlin
class MainActivity : IstmoGameActivity()
```

Before the Rust entry point runs it loads the library named by the
activity's `android.app.lib_name` meta-data, starts `IstmoRuntime` once
per process and registers every plugin with the activity as host. An
app with its own activity calls `IstmoHost` instead:

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    IstmoHost.onCreate(this) // before super.onCreate
    super.onCreate(savedInstanceState)
}

override fun onDestroy() {
    super.onDestroy()
    IstmoHost.onDestroy(this)
}
```

### iOS

For crates with a `#[istmo::mobile_app]` entry point, `istmo-build`
generates `Plugins/IstmoMain.swift`, and `main.swift` is one line:

```swift
import IstmoRuntime

IstmoApp.run()
```

It starts the runtime, calls `IstmoPluginRegistry.registerAll()` and
hands control to Rust. The entry point is detected from the crate
sources; set `[app] rust_entry = true | false` to override. Native-UI
apps call `IstmoPluginRegistry.registerAll()` after
`IstmoRuntime.shared.start()`.

## The generated files

The Kotlin registry always lives at `dev.istmo.generated.IstmoPluginRegistry`
(`android/app/src/main/java/dev/istmo/generated/`), so `IstmoHost` finds
it without configuration:

```kotlin
// GENERATED by istmo-build - DO NOT EDIT.
package dev.istmo.generated

object IstmoPluginRegistry : IstmoPluginRegistrant {
    override fun registerAll(context: Context) {
        IstmoRuntime.registerHandler(
            com.myapp.gen.DataStoreDispatcher.PLUGIN_ID,
            com.myapp.gen.DataStoreDispatcher(
                dev.istmo.plugins.datastore.DataStoreFactoryImpl(context),
                com.myapp.gen.DataStoreCodecsImpl(),
            ),
        )
        hostActivity<androidx.activity.ComponentActivity>(context, "istmo.share")?.let { activity ->
            IstmoRuntime.registerHandler(
                com.myapp.gen.ShareDispatcher.PLUGIN_ID,
                com.myapp.gen.ShareDispatcher(
                    dev.istmo.plugins.share.ShareBackendImpl(activity),
                    com.myapp.gen.ShareCodecsImpl(),
                ),
            )
        }
    }
    // …
}
```

The iOS mirror lives at `ios/<AppDir>/Plugins/IstmoPluginRegistry.swift`.
Both are regenerated on every build (and emitted even when empty); add
them to `.gitignore`.

## What "eligible" means

A plugin appears in the registry when **all** of these hold:

- The plugin's role is `host` (the native side implements the backend).
  `client` role plugins do not register a dispatcher — they generate a
  `<T>Client` for the native side to call.
- The plugin's `istmo.toml` has `auto_register = true` (default).
- The app's `istmo.toml` does not override with `auto_register = false`
  for that plugin.
- The app-level `[app] auto_register` is not `false`.

## Construction

- **Stateless plugins**: `<T>Dispatcher(<backend>, <T>CodecsImpl())`.
- **Stateful plugins** (trait declared with `init = Config`): the class
  is a factory that materialises a backend per instance.

The plugin's `istmo.toml` says which class and what it receives:

```toml
[plugin]
id                  = "istmo.share"
android_backend     = "dev.istmo.plugins.share.ShareBackendImpl"
android_backend_arg = "activity"
ios_backend         = "ShareBackendImpl"
```

- **`android_backend`** — fully-qualified Kotlin class. Default:
  `<T>BackendImpl` / `<T>FactoryImpl` in the app's codegen package.
- **`android_backend_arg`** — `"context"` (default), `"activity"`
  (`androidx.activity.ComponentActivity`) or a fully-qualified
  `Activity` subclass such as `"androidx.fragment.app.FragmentActivity"`.
  Activity-bound plugins are skipped with a log line when the registry
  runs without an activity (e.g. from a `Service`), and fail loudly when
  the host activity is not of the required type.
- **`ios_backend`** — Swift type, constructed with no arguments.
  Default: `<T>BackendImpl` / `<T>FactoryImpl`.

## Opting out

### Per plugin (plugin author)

For backends whose construction varies per app (an API key, a view the
app owns):

```toml
[plugin]
id            = "acme.push_notifications"
client_type   = "::acme_push::PushClient"
auto_register = false
```

### Per plugin (app author)

```toml
[[app.plugin]]
id            = "istmo.data_store"
auto_register = false
```

The registry omits the plugin; register it yourself after
`IstmoHost.onCreate(this)` (Android) or inside
`IstmoApp.run(registerPlugins:entry:)` (iOS).

### Globally

```toml
[app]
auto_register = false
```

The registries are still generated, empty.

## Debugging

If the registry is missing a plugin you expected:

- Confirm the plugin's `istmo.toml` doesn't set `auto_register = false`.
- Confirm you don't have a matching `[[app.plugin]]` override in your
  app.
- Confirm you're not using `role = "client"` for that plugin.
