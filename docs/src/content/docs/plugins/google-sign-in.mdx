`istmo-google-sign-in` wraps the platform-idiomatic Google Sign-In
flows behind a single Rust trait.

- **Android** uses `androidx.credentials` (Credential Manager) plus
  the `googleid` provider. Minimum API 21 (declared in the plugin's
  `[min_versions]`).
- **iOS** uses the official `GoogleSignIn` SwiftPM package (7.1+, for
  the `nonce:` parameter).

There is no desktop backend.

Both flows return an opaque credential handle; the token material
stays on the native side and is released when the Rust handle drops.

## Install

```toml
[dependencies]
istmo-google-sign-in = "0.1.1-alpha.5"
```

Rebuild your app; `istmo_build::emit()` picks up the plugin's Gradle +
SwiftPM entries automatically. Platform setup is limited to the OAuth
clients below.

## Configure the OAuth clients

In the [Google Cloud
Console](https://developers.google.com/identity), in one project,
create:

- One **Web** OAuth client — its id is `server_client_id`: the
  `serverClientId` on Android and the id-token audience on iOS.
- On Android, an **Android** OAuth client for the app's package name
  and signing-certificate SHA-1.
- On iOS, an **iOS** OAuth client (see [iOS specifics](#ios-specifics)).

The plugin is stateful (`init = SignInConfig`), so you pass the
configuration when acquiring the client:

```rust
use istmo_google_sign_in::{SignInClient, SignInConfig, SignInMode};

let cfg = SignInConfig::builder("1234-web.apps.googleusercontent.com")
    .scope("email")
    .scope("profile")
    .auto_select(false)
    .build();

let sign_in = SignInClient::from_runtime_with(&runtime, cfg).await?;
// …or on the process-global runtime: SignInClient::acquire_with(cfg).await?
```

Other builder methods: `.scopes(iter)`, `.hosted_domain(...)` for
Google Workspace tenants and `.nonce(...)` for replay protection.
`Debug` output of `SignInConfig`, `SignInAccount` and
`OwnedSignInAccount` redacts the nonce and the id token.

## Sign in

```rust
use istmo_google_sign_in::SignInError;

let account = sign_in
    .sign_in_owned(SignInMode::Interactive)
    .await
    .map_err(SignInError::from)?;

tracing::info!("signed in as {:?}", account.email);
send_to_server(&account.id_token); // verify it server-side
// account.credential: NativeHandle<Credential>
```

`SignInMode::Interactive` shows the account chooser;
`SignInMode::SilentOnly` fails with `SignInError::NoCredentialAvailable`
instead of prompting when no cached credential exists.
`silent_sign_in_owned()` returns `Option<OwnedSignInAccount>` — `None`
instead of that error.

`SignInError::from` decodes the plugin's own error from the client's
`IstmoError`. The backends do not verify the id token; your server
must.

Use the `_owned` variants unless you specifically need to re-ship the
raw `NativeHandleId` — they adopt the credential into a
`NativeHandle<Credential>` that releases it on drop. The raw
`sign_in` / `silent_sign_in` / `refresh` return `SignInAccount` with a
bare id; `SignInAccount::into_owned(&runtime)` adopts it later.

## Refresh

`refresh` takes the current credential id and returns the account under
a new credential id. The old id is consumed: its handle becomes stale
(dropping it is a no-op) and the new handle is released independently:

```rust
let refreshed = sign_in.refresh_owned(account.credential.id()).await?;
drop(account);
```

On iOS the SDK refreshes the tokens of the signed-in user; on Android
Credential Manager has no refresh, so the silent flow runs again
(failing with `SignInError::Reauthenticate` when there is no
credential).

## Sign out and revoke

```rust
sign_in.sign_out().await?;
sign_in.revoke().await?;
```

Both drop every credential the backend holds; handles your Rust code
still owns become stale and their release is a no-op. `revoke` also
disconnects the app from the account on iOS
(`GIDSignIn.disconnect`). On Android it only clears the local
credential state — revoke the grant from your server
(`https://oauth2.googleapis.com/revoke`).

## Android limits

Credential Manager authenticates; it does not grant OAuth scopes.
Extra `SignInConfig::scopes` are ignored and `granted_scopes` only
lists `openid`, `email` and `profile`. Silent sign-in uses
auto-select, so with exactly one authorised account the system still
flashes a short "signing you in" banner.

## Android specifics

The plugin declares its Gradle deps via `istmo.toml`:

```toml
[[gradle]]
group    = "androidx.credentials"
artifact = "credentials"
version  = "1.3.0"

[[gradle]]
group    = "androidx.credentials"
artifact = "credentials-play-services-auth"
version  = "1.3.0"

[[gradle]]
scope    = "api"
group    = "com.google.android.libraries.identity.googleid"
artifact = "googleid"
version  = "1.1.1"
```

Nothing to add to your app-side `build.gradle.kts` — the entries flow
through `istmo-build`'s native-dep handover.

The Credential Manager flow needs an `Activity`. The plugin declares
`android_backend_arg = "activity"`, so the generated registry hands
`GoogleSignInFactoryImpl` the host activity (`IstmoGameActivity` is
one).

## iOS specifics

The plugin declares the Swift package:

```toml
[[swift_package]]
url          = "https://github.com/google/GoogleSignIn-iOS.git"
product      = "GoogleSignIn"
from_version = "7.1.0"
```

The backend reads the iOS OAuth client id from `GIDClientID` in the
app's `Info.plist` (the SDK's own convention; without it sign-in fails
with `SignInError::InvalidConfiguration`). Set it from the app's
`istmo.toml`:

```toml
[app.info_plist]
GIDClientID = "1234-ios.apps.googleusercontent.com"
```

The SDK also expects the reversed client id under
`CFBundleURLTypes` → `CFBundleURLSchemes` in `Info.plist`, and
`application(_:open:options:)` forwarded to
`GIDSignIn.sharedInstance.handle(_:)`.

## Wire it up

`SignIn` is stateful (it carries an OAuth configuration per instance),
so the generated `IstmoPluginRegistry` registers it through the
plugin's `GoogleSignInFactoryImpl` (`android_backend` / `ios_backend`
in its `istmo.toml`). The Gradle plugin and the `istmo-plugins.yml`
xcodegen fragment compile the plugin's native sources into the app, so
there is nothing to copy.

```kotlin
// IstmoGameActivity, the template's launcher, already does this.
// An app with its own activity calls IstmoHost before super.onCreate:
override fun onCreate(savedInstanceState: Bundle?) {
    IstmoHost.onCreate(this) // starts the runtime + IstmoPluginRegistry
    super.onCreate(savedInstanceState)
}
```

```swift
// ios/<Name>App/main.swift
import IstmoRuntime

IstmoApp.run() // starts the runtime + IstmoPluginRegistry, then runs Rust
```

See [Auto-registration](/istmo/build-scripts/auto-register/) for the full
mechanism and opt-out flags.

## Reference backends

The plugin ships its backends under `plugins/google-sign-in/native/`:

- `android/GoogleSignInBackendImpl.kt` + `GoogleSignInFactoryImpl.kt`
  (package `dev.istmo.plugins.googlesignin`, where `istmo-build` also
  generates the plugin's Kotlin)
- `ios/GoogleSignInBackendImpl.swift` (also defines
  `GoogleSignInFactoryImpl`)

They are compiled into every app that depends on the crate. To
customise one, set `auto_register = false` for `istmo.google_sign_in`
in the app's `[[app.plugin]]` and register your own backend.
