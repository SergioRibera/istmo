# High-rate data without the bus

Design for moving high-rate data (stream items, video frames, audio
buffers) between an istmo plugin and its consumer without paying the
frame protocol's encode / route / decode cost per item. Covers:

- **(a)** the typed in-process shortcut for `#[stream]` methods,
- **(b)** native frame sinks: a typed, per-session channel for buffers
  that must never be serialised (DMA-BUF, `AHardwareBuffer`,
  `CVPixelBuffer` / `IOSurface`, D3D11 textures, shared CPU memory),
- **(c)** the Android / iOS entry that hands a native buffer to Rust
  directly, generated by `istmo-build` like the rest of the bridge,
- **(d)** what happens when the consumer is across the bus,
- **(e)** how existing plugins benefit (camera).

Status: (a)–(d) implemented in `istmo-core`, `istmo-macros`,
`istmo-build`, `istmo-android`, `istmo-ios` and the Kotlin / Swift
runtimes. Camera migration (e) is described, not done.

## Why

What a plugin pays per stream item today:

| Path | Per item |
|---|---|
| Rust host → Rust client (same runtime) | encoder thread receives `T`, `codec::encode` into a fresh `Vec<u8>`, flume hop to the pump, pump looks up the stream in the routing table, flume hop to the `StreamHandle`, `codec::decode` into a fresh `T` |
| Kotlin / Swift host → Rust client | native encode into `ByteArray` / `Data`, JNI / FFI copy into `Vec<u8>`, `Frame::Event` dispatch, routing, decode |

For a 1080p NV12 frame (3 MB) that is three to four full copies plus
two allocations per frame, before the consumer touches a pixel.
ferricast rejected istmo streams for its codec data plane for exactly
this reason (`ferricast/design/CODECS.md`, "istmo plugin"), and every
media plugin so far (camera, webview presentation) grew its own
out-of-band path. The webview's `FrameSink` registry
(`plugins/webview/src/present.rs`) is the in-process precedent this
design generalises.

Non-goals:

- No new wire frames. Nothing here changes `Frame`, so
  `PROTOCOL_VERSION` stays 4.
- No cross-process buffer sharing (yet): see (d).
- No GPU API in istmo. istmo moves ownership of a buffer; importing it
  into Vulkan / Metal / D3D is the consumer's business.

## (a) Typed stream shortcut

### Today

`#[istmo::plugin]` emits `<Trait>Typed` for stateless plugins: one
boxed-future method per unary trait method. `<Trait>Host::register(rt)`
installs the host both as a wire dispatcher and as the typed slot
(`Runtime::register_typed_host`). The generated client checks the slot
(one atomic load when no typed host exists) and calls through it — no
encode, no routing, no thread. Stream methods were skipped.

### Change

`<Trait>Typed` gains one method per `#[stream]` method:

```rust
fn frames(&self, session: NativeHandleId, __istmo_cancel: CancelToken)
    -> flume::Receiver<CameraFrame>;               // or Receiver<Result<T, E>>
```

The host's impl forwards to the trait implementation, filling every
`CancelToken` argument with the token it was given. The client's stream
method tries the typed slot first:

1. `Runtime::open_local_stream()` registers a fresh `CancelToken` in the
   runtime's hosted-call table under a new stream id (so `shutdown`
   trips it like any hosted stream).
2. The implementation is called on the caller's thread, inside
   `catch_unwind` (a panic surfaces as `IstmoError::PluginError` with
   the same `"host panicked"` payload as the unary shortcut).
3. The producer's own `flume::Receiver` is wrapped in the returned
   `TypedStream` — no extra channel, no encoder thread, no pump.

`TypedStream<Item, Err>` keeps its public shape (`recv`, `recv_async`,
`try_recv`, `StreamItem`). Internally it is either the wire handle or
the local receiver:

| Event | Wire | Local |
|---|---|---|
| item | decode bytes | the producer's value, moved |
| `Result` stream `Err(e)` | `StreamEnd::Error` → `Failed(e)` | `Failed(e)`, then the stream counts as ended |
| producer drops its sender | `StreamEnd::Complete` → `Completed` | `Completed` |
| runtime shutdown / cancel | `Cancelled` | `Cancelled` (token checked before each item, raced while waiting) |
| consumer drops the stream | `Cancel` frame / hosted token | hosted token tripped; the producer's `send` fails once the receiver is gone |

`stream_id()` keeps working (local streams get an id from the same
counter); `into_inner()` became `into_wire() -> Option<StreamHandle>`
(no shim: nothing ships before the first release).

Per-item cost on the local path: one atomic load (cancelled?) plus
flume's `try_recv`; only a consumer that has to wait builds the
`recv_async` / `cancelled()` race. Bounded or unbounded, latest-value
or lossless — the producer's channel choice is the policy.

### Rules (unchanged from the unary shortcut)

- Stateless plugins only. Stateful (`init = …`) plugins route by
  instance id; an instance-keyed typed slot is a follow-up.
- Opt-in: `<Trait>Host::register(rt)`. `RuntimeInit::host` /
  `istmo::runtime!(hosts: …)` keep registering the wire dispatcher
  only, because the typed path runs the implementation on the caller's
  thread (a stream method that blocks before returning its receiver
  blocks the caller).
- Remote and native callers keep using the wire path; both paths are
  live at once.

### Rejected

- Running the typed stream method on a spawned thread "for safety": it
  re-adds the thread spawn the shortcut exists to remove; the opt-in
  already states the contract.
- A separate `local_frames()` client method: callers should not choose
  the path; the runtime knows where the host is.
- Wrapping local items in a second channel to unify the receive code:
  that is the extra hop (a)'s goal forbids.

## (b) Native frame sinks

A frame sink is a per-session, typed, bounded mailbox owned by the
consumer and fed by a producer that may be Rust (a desktop backend), a
Kotlin backend (through JNI) or a Swift backend (through the C ABI).
Each item is a `NativeFrame<M>`: plugin-defined metadata `M` plus a
`NativeBuffer` whose drop releases the memory to whoever produced it.

### Types (`istmo_core::native_frame`)

```rust
pub struct FrameSinkId<M> { /* u64 + PhantomData<fn() -> M> */ }   // Copy, wire = u64
pub struct FrameSink<M>   { /* consumer end, not Clone */ }
pub struct FrameSender<M> { /* producer end, Clone */ }
pub struct NativeFrame<M> { pub meta: M, pub buffer: NativeBuffer, /* seq, dropped_before */ }
pub struct NativeBuffer   { /* Arc<backing + release hook> */ }       // Clone shares
pub struct SinkPolicy     { /* depth: NonZeroUsize, overflow: Overflow */ }
pub enum Overflow { DropOldest, DropNewest }
pub enum MemoryKind { Cpu, DmaBuf, HardwareBuffer, CvPixelBuffer, IoSurface, D3d11Texture, Other }
pub struct SinkStats { pub accepted: u64, pub delivered: u64, pub dropped: u64 }
```

Opening, by the consumer:

```rust
let sink: FrameSink<CaptureMeta> = rt.open_frame_sink(SinkPolicy::latest());
client.start(config, sink.id()).await?;          // FrameSinkId<CaptureMeta> is a wire arg
while let Some(frame) = sink.recv_async().await {
    let meta: &CaptureMeta = &frame.meta;
    if let Some(dmabuf) = frame.buffer.dmabuf() { /* import planes */ }
    // dropping `frame` releases the buffer to the producer
}
```

Producing, by a Rust host in the same process:

```rust
async fn start(&self, config: Config, sink: FrameSinkId<CaptureMeta>) -> Result<(), E> {
    let sender = self.runtime()?.frame_sender(sink)?;    // typed downcast, no bytes
    spawn_capture(move |pixels, meta| {
        let buffer = NativeBuffer::from_dmabuf(pixels).with_release(return_to_pool);
        if sender.push(meta, buffer).is_err() { /* consumer gone: stop */ }
    });
    Ok(())
}
```

`FrameSinkId<M>` is an ordinary wire value, so the trait method that
takes it is an ordinary plugin method: the same contract works for a
Rust host, a Kotlin host or a Swift host.

### Ownership, leases, release

- `NativeBuffer` owns one backing value (`Box<dyn Any + Send + Sync>`)
  and an optional release hook. The backing's own `Drop` releases what
  it owns (closes DMA-BUF fds, `AHardwareBuffer_release`,
  `CFRelease`, `Release` on a COM pointer); the hook (`with_release`)
  runs after it, for pooled producers that need to know the buffer is
  free again (wlr-screencopy / ext-image-copy buffer pools, PipeWire
  buffers held until the consumer is done, `ImageReader` images).
- `NativeBuffer: Clone` shares the backing (`Arc`); release fires when
  the last clone drops. Fan-out to several consumers needs no copy.
- `into_backing::<B>()` takes the backing out when the buffer is not
  shared and returns a `BufferLease` that fires the hook on drop, so a
  consumer can move DMA-BUF fds into its own types (ferricast's
  `DmaBufFd`) and keep the producer's pool slot reserved for as long as
  it holds the lease.
- Core ships two constructors: `from_cpu` (the backing is any
  `AsRef<[u8]> + Send + Sync` owner — `Vec<u8>`, `Bytes`, an mmap, a JNI
  direct `ByteBuffer` — read with `cpu_bytes()`) and, on Unix, `DmaBuf` (planes of `OwnedFd` + offset + stride, fourcc,
  modifier, size). Platform backings live where they are created:
  `istmo_android::HardwareBuffer`, `istmo_ios::RetainedBuffer`, and
  plugin-owned types (a D3D11 texture, an `IOSurface`). Consumers
  downcast with `buffer.downcast_ref::<T>()`; `kind()` names the
  memory without a downcast.

### Backpressure

The producer never blocks. `SinkPolicy` decides what a full sink does:

| Policy | Depth | Full sink | Use |
|---|---|---|---|
| `SinkPolicy::latest()` | 1 | replace the queued frame (`DropOldest`) | previews, screen mirroring, anything where stale frames are worthless |
| `SinkPolicy::queue(n)` | n | evict the oldest (`DropOldest`) | encoders that want every frame but tolerate a hiccup |
| `SinkPolicy::queue(n).with_overflow(Overflow::DropNewest)` | n | refuse the new frame | consumers that must keep a contiguous prefix (audio) |

Every drop is counted: the next delivered frame carries
`dropped_before()` (frames lost since the previous delivery — camera's
existing convention), and `stats()` keeps lifetime totals on both ends.
Evicted frames are dropped outside the sink's lock, so their release
(JNI, CoreFoundation) never runs under it. A producer whose push was
refused gets its frame back (`PushError::Full` / `Closed`) and decides
whether to release or retry.

A blocking policy was rejected: it would stall capture threads and
native callbacks (`ImageReader.OnImageAvailableListener`, ReplayKit's
sample handler) that must return quickly.

### Lifetime

- The sink ends when the consumer drops `FrameSink` (producers see
  `Closed` on their next push; native producers get status `CLOSED`),
  when a producer calls `close()` (or the last clone of a
  `FrameSender` drops), or at `Runtime::shutdown` (every sink closes;
  queued frames are released).
- `FrameSink::recv*` returns `None` once the sink is closed and empty;
  frames queued before a producer close are still delivered.
- Ids come from the runtime's id counter and are only meaningful inside
  the runtime that opened them. A stale id resolves to
  `IstmoError::UnknownFrameSink`; a sink opened for `M` resolved as
  another type fails with `IstmoError::FrameSinkTypeMismatch`.

### Threading

- `FrameSender::push` is callable from any thread, is O(1) under one
  short mutex and never waits. Wake-up is a capacity-1 flume doorbell,
  so `recv_async` works on any executor and `recv` blocks a thread.
- `FrameSink` is `Send + Sync` but meant for one consumer: two
  concurrent receivers split the frames between them.
- Release (backing drop + hook) runs on the thread that drops the last
  reference: the consumer thread normally, the producer thread for an
  evicted frame, the shutdown caller at shutdown. Backings must
  therefore be thread-safe to drop, which every platform object listed
  here is (the JNI backing attaches the thread through `GlobalRef`'s
  drop).

### Relationship to webview's `FrameSink`

The webview registry is a latest-value slot of a plain `Copy` value
keyed by view. It keeps its own trait (its frames are placements, not
buffers, and its engines read the slot from a UI tick, not a
receiver), but a future cleanup can express it as
`open_frame_sink::<ViewFrame>(SinkPolicy::latest())` with a CPU-less
buffer. Not done now: no behaviour gain, and it would churn six
engines.

## (c) Mobile entry: native buffers straight to Rust

The FFI rule stands: no per-feature trampolines, envelopes never cross
the boundary. The runtime crates gain **one generic entry per buffer
family**; codegen gives each plugin a typed wrapper on top.

### Android

`istmo-android` exports (bound by `dev.istmo.runtime.IstmoRuntime`):

| Kotlin `external fun` | Rust behaviour |
|---|---|
| `nativeSubmitHardwareBuffer(sink: Long, buffer: HardwareBuffer, meta: ByteArray): Int` | `AHardwareBuffer_fromHardwareBuffer` + `AHardwareBuffer_acquire` (one reference for Rust; `AHardwareBuffer_describe` captured), wrap in `HardwareBuffer` backing, decode nothing — hand `meta` bytes to the sink, which decodes `M` |
| `nativeSubmitDirectBuffer(sink: Long, buffer: ByteBuffer, length: Int, meta: ByteArray): Int` | zero-copy view of a direct `ByteBuffer` held by a JNI `GlobalRef` |
| `nativeSubmitFrameBytes(sink: Long, bytes: ByteArray, meta: ByteArray): Int` | one copy into a CPU buffer (heap arrays cannot be pinned safely past the call) |
| `nativeCloseFrameSink(sink: Long)` | producer-side close |

The NDK functions are resolved with `dlsym` on first use, not linked:
`AHardwareBuffer_fromHardwareBuffer` is API 26, and a hard link would
make the whole `.so` fail to load on older devices. Below API 26 the
entry answers `UNSUPPORTED`.

The `Int` status is `SubmitStatus` (`0 ACCEPTED`, `1 DISPLACED` — taken,
an older frame was evicted by the policy, `2 CLOSED`, `3 UNKNOWN_SINK`,
`4 BAD_META`, `5 UNSUPPORTED`, `6 NOT_STARTED`, `7 INVALID`, `8 FULL` —
refused by a `DropNewest` sink). On every status other than
`ACCEPTED` / `DISPLACED` Rust did not keep a
reference, so the caller still owns its own (it always does: Rust
acquires its own reference and Kotlin closes its `HardwareBuffer` /
`Image` whenever it likes).

### iOS

`istmo-ios` exports, declared in `istmo_ffi.h`:

```c
int32_t istmo_ios_submit_native_buffer(uint64_t sink, uint32_t kind,
    void *object, void (*release)(void *),
    const uint8_t *meta, size_t meta_len);
int32_t istmo_ios_submit_frame_bytes(uint64_t sink,
    const uint8_t *bytes, size_t len, const uint8_t *meta, size_t meta_len);
void istmo_ios_close_frame_sink(uint64_t sink);
```

Swift passes `Unmanaged.passRetained(pixelBuffer).toOpaque()` plus a
`@convention(c)` release function; Rust owns that +1 and calls
`release` exactly once (on drop, or immediately when the submit is
refused). `kind` is `CvPixelBuffer` / `IoSurface` / `CmSampleBuffer` /
`Other`. No framework is linked from Rust, so the crate keeps building
and testing on Linux; consumers that need Core Video use `objc2-core-video`
on the pointer from `RetainedBuffer::as_ptr()`.

### Generated surface

A plugin method argument `sink: FrameSinkId<CaptureMeta>` becomes, in
the contract, `TypeRef::FrameSink(Named("CaptureMeta"))`. Generators:

- **Kotlin**: the backend receives `IstmoFrameSink<CaptureMeta>`
  (`dev.istmo.runtime`), built by the dispatcher from the wire id and
  an encoder lambda over `<T>Codecs.writeCaptureMeta`. Methods:
  `submit(buffer: HardwareBuffer, meta: M)`, `submit(buffer: ByteBuffer, length: Int, meta: M)`,
  `submitBytes(bytes, meta)`, `close()`, each returning `IstmoSubmitStatus`.
- **Swift**: `IstmoFrameSink<CaptureMeta>` (`IstmoRuntime`) with
  `submitRetained(_:kind:release:meta:)`, `submitBytes(_:meta:)` and
  `close()` in `IstmoFrameSink.swift` (Foundation only, type-checked on
  Linux), plus `submit(_ pixelBuffer: CVPixelBuffer, meta:)` and
  `submit(_ surface: IOSurfaceRef, meta:)` behind `#if canImport(…)` in
  `IstmoFrameSink+Apple.swift`. The closure capturing `codecs` is
  emitted only when the metadata names a declared type (swiftc warns on
  unused captures).
- Rust client / host code needs nothing generated: `FrameSinkId<M>` is
  the Rust type on both sides.

The wire layout is the `u64` id (`writeU64` / `readVarintU64`, same as
`NativeHandleId`), pinned in `crates/build/tests/native_wire.rs`.

### Rejected

- A `NativeHandle`-based buffer registry (native keeps the buffer,
  Rust gets an id and calls back to lock it): one JNI round trip per
  access, and the native side would need a second lifetime system.
- Decoding `M` on the native side and passing fields as JNI arguments:
  per-plugin trampolines, forbidden.
- Linking `CoreVideo` / `libandroid` symbols from the transport crates:
  breaks Linux tests, and on Android makes old API levels fail to load
  the library.

## (d) Consumer across the bus

Sink ids are process-local. There is no silent fallback:

| Situation | Result |
|---|---|
| Rust consumer, Rust host, same runtime | zero-copy push |
| Rust consumer, Kotlin / Swift host, same process | zero-copy native entry |
| Kotlin / Swift consumer of a Rust-hosted producer | not supported by sinks; consumers on that side use the plugin's own native API |
| Consumer in a `:remote` process, or any runtime other than the one that opened the sink | producer's `frame_sender` fails with `UnknownFrameSink`; native entry answers `UNKNOWN_SINK`; the plugin must fail the call with a domain error |

`Runtime::shares_native_frames(plugin_id)` is `false` for plugins
declared remote, so a client can refuse before sending the id.
Plugins that want remote consumers expose an explicit CPU path — an
ordinary `#[stream]` of an encoded / copied frame type — and say so in
their capability report; the copy is then visible in the API. Future
work, when a consumer needs it: shuttle `HardwareBuffer` (Parcelable)
and DMA-BUF fds (`SCM_RIGHTS`) through the remote bridge.

## (e) Existing plugins

**Camera** copies every frame today: `CameraFrame { bytes: Vec<u8> }`
is filled by `extractPlanes` / `toNv21` in Kotlin and by a
`CVPixelBuffer` lock + copy in Swift, encoded, sent as `Frame::Event`,
decoded in Rust, and fanned out by cloning. Migration (not done here):

1. Add `#[owned] async fn open_frames(&self, session: NativeHandleId,
   sink: FrameSinkId<FrameInfo>) -> Result<(), CameraError>` where
   `FrameInfo` is `CameraFrame` without `bytes` (planes, rotation,
   timestamps, format).
2. Android: `ImageReader` with `HardwareBuffer` usage (API 28+:
   `Image.getHardwareBuffer()`), `sink.submit(image.hardwareBuffer, info)`,
   close the `Image` right away (Rust holds its own reference) — the
   pool depth becomes the `ImageReader`'s `maxImages`, back-pressure the
   sink policy. Below API 28, `submitBytes` (one copy instead of four).
3. iOS: `sink.submit(CMSampleBufferGetImageBuffer(sample), info)` from
   the `AVCaptureVideoDataOutput` delegate.
4. Desktop (nokhwa): `NativeBuffer::from_cpu(frame_bytes)` — the buffer
   nokhwa already allocated, moved instead of re-encoded; V4L2
   `VIDIOC_EXPBUF` DMA-BUF export is a later step.
5. `SessionHandle::frames()` keeps the copying `TypedStream` for
   callers that want plain bytes; `SessionHandle::native_frames(policy)`
   is the new path. `FrameFanout` goes away for native frames
   (`NativeBuffer: Clone` shares).

Camera's plugin is stateful, so (a) does not apply to it until the
typed shortcut learns instances; (b) does not care.

**Webview** keeps its own sink (see above). **ferricast's codec
plugin** can move its data plane onto sinks instead of the side
channel it uses now.

## Measurements

`crates/core/benches/stream_paths.rs` (criterion 0.7, `cargo bench`,
AMD Ryzen 9 9950X3D, Linux 6.18, rustc 1.95). Every variant allocates its
payload with `vec![0; n]` on the producer side, so rows differ by
transport only.

Pipelined: a producer thread streams a batch (2 000 items of 16 B, or
16 items of 8 MiB) to the consumer; time per item:

| Path | 16 B | 8 MiB |
|---|---|---|
| bus stream (encoder thread, pump, routing, decode) | 391 ns | 1 058 µs |
| typed stream shortcut | 356 ns | 71 µs |
| frame sink, Rust producer | 329 ns | 64 µs |
| frame sink, native entry (`submit_native_frame`, meta decoded) | 488 ns | 62 µs |

Single thread, one item handed over and taken back (no scheduler
wake-ups):

| Path | 16 B |
|---|---|
| flume hand-off (what the typed shortcut leaves) | 23 ns |
| encode + channel + decode (bus minus its two thread hops) | 43 ns |
| frame sink push + try_recv (one allocation per buffer) | 43 ns |
| frame sink native submit (meta decoded) + try_recv | 64 ns |

Reading: for large buffers both new paths remove the two full copies
(15× at 8 MiB; what remains is the producer's own allocation). For
small items everything is bound by cross-thread hand-off; the shortcut
still saves the encoder thread and the pump per stream, and sinks are
not meant for tiny items a stream carries just as well. Two sink
optimisations came out of these runs: one allocation per buffer
(backing and hooks in a single `Arc`), and ringing the doorbell only
when the consumer found the queue empty.

## Open questions

1. Should `istmo::runtime!(hosts: …)` install the typed shortcut for
   stateless hosts automatically (via a `Dispatch::typed_slot` hook)?
   Faster by default, but changes which thread a host method runs on.
2. Stateful typed shortcut (instance-keyed slots) — needed for camera
   to benefit from (a).
3. Cross-process buffers (Binder `HardwareBuffer`, `SCM_RIGHTS`
   DMA-BUF, XPC `IOSurface`) — wait for a consumer.
4. Should `FrameSink` offer a `Stream` impl (futures-core) for `select!`
   users? Today `recv_async` only, matching `TypedStream`.
