El auto-wiring del lado Rust recoge los **clients** de plugins
transparentemente vía `istmo::runtime!` (ver
[Auto-wiring](/istmo/es/advanced/auto-wiring/)). El lado nativo necesita su
propio mecanismo porque los **backends** de plugin —
`<T>BackendImpl.kt` / `<T>BackendImpl.swift` — son clases nativas que
el runtime tiene que construir.

`istmo-build` cierra el gap emitiendo un **`IstmoPluginRegistry`**
dentro de tu app, y el runtime trae entry points que lo llaman: el
equivalente al `GeneratedPluginRegistrant` + `FlutterActivity` de
Flutter.

## Entry points

### Android

Usá `IstmoGameActivity` (para UIs basadas en `GameActivity`, p. ej.
winit / eframe con `android-game-activity`) o `IstmoNativeActivity`
(`NativeActivity`) como tu activity, directo en el manifest o como una
subclase vacía:

```kotlin
class MainActivity : IstmoGameActivity()
```

Antes de que corra el entry point de Rust, carga la librería que nombra
el meta-data `android.app.lib_name` de la activity, arranca
`IstmoRuntime` una vez por proceso y registra cada plugin con la activity
como host. Una app con su propia activity llama a `IstmoHost`:

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    IstmoHost.onCreate(this) // antes de super.onCreate
    super.onCreate(savedInstanceState)
}

override fun onDestroy() {
    super.onDestroy()
    IstmoHost.onDestroy(this)
}
```

### iOS

Para crates con un entry point `#[istmo::mobile_app]`, `istmo-build`
genera `Plugins/IstmoMain.swift`, y `main.swift` queda en una línea:

```swift
import IstmoRuntime

IstmoApp.run()
```

Arranca el runtime, llama a `IstmoPluginRegistry.registerAll()` y le
pasa el control a Rust. El entry point se detecta en las fuentes del
crate; seteá `[app] rust_entry = true | false` para forzarlo. Las apps
con UI nativa llaman a `IstmoPluginRegistry.registerAll()` después de
`IstmoRuntime.shared.start()`.

## Los archivos generados

El registry de Kotlin vive siempre en
`dev.istmo.generated.IstmoPluginRegistry`
(`android/app/src/main/java/dev/istmo/generated/`), así `IstmoHost` lo
encuentra sin configuración:

```kotlin
// GENERATED by istmo-build - DO NOT EDIT.
package dev.istmo.generated

object IstmoPluginRegistry : IstmoPluginRegistrant {
    override fun registerAll(context: Context) {
        IstmoRuntime.registerHandler(
            com.myapp.gen.DataStoreDispatcher.PLUGIN_ID,
            com.myapp.gen.DataStoreDispatcher(
                dev.istmo.plugins.datastore.DataStoreFactoryImpl(context),
                com.myapp.gen.DataStoreCodecsImpl(),
            ),
        )
        hostActivity<androidx.activity.ComponentActivity>(context, "istmo.share")?.let { activity ->
            IstmoRuntime.registerHandler(
                com.myapp.gen.ShareDispatcher.PLUGIN_ID,
                com.myapp.gen.ShareDispatcher(
                    dev.istmo.plugins.share.ShareBackendImpl(activity),
                    com.myapp.gen.ShareCodecsImpl(),
                ),
            )
        }
    }
    // …
}
```

El espejo de iOS vive en `ios/<AppDir>/Plugins/IstmoPluginRegistry.swift`.
Ambos se regeneran en cada build (y se emiten aunque estén vacíos);
agregalos al `.gitignore`.

## Qué significa "elegible"

Un plugin aparece en el registry cuando se cumple **todo** esto:

- El rol del plugin es `host` (el lado nativo implementa el backend).
  Los plugins con rol `client` no registran dispatcher: generan un
  `<T>Client` para que lo llame el lado nativo.
- El `istmo.toml` del plugin tiene `auto_register = true` (default).
- El `istmo.toml` de la app no lo pisa con `auto_register = false`
  para ese plugin.
- `[app] auto_register` no es `false`.

## Construcción

- **Plugins stateless**: `<T>Dispatcher(<backend>, <T>CodecsImpl())`.
- **Plugins stateful** (trait declarado con `init = Config`): la clase
  es una factory que materializa un backend por instancia.

El `istmo.toml` del plugin dice qué clase y qué recibe:

```toml
[plugin]
id                  = "istmo.share"
android_backend     = "dev.istmo.plugins.share.ShareBackendImpl"
android_backend_arg = "activity"
ios_backend         = "ShareBackendImpl"
```

- **`android_backend`**: clase Kotlin completamente calificada. Default:
  `<T>BackendImpl` / `<T>FactoryImpl` en el package de codegen de la app.
- **`android_backend_arg`**: `"context"` (default), `"activity"`
  (`androidx.activity.ComponentActivity`) o una subclase de `Activity`
  completamente calificada, como `"androidx.fragment.app.FragmentActivity"`.
  Los plugins atados a una activity se saltean (con un log) cuando el
  registry corre sin activity (p. ej. desde un `Service`), y fallan con
  un error claro cuando la activity host no es del tipo requerido.
- **`ios_backend`**: tipo Swift, construido sin argumentos. Default:
  `<T>BackendImpl` / `<T>FactoryImpl`.

## Opt-out

### Por plugin (autor del plugin)

Para backends cuya construcción varía por app (una API key, una view de
la app):

```toml
[plugin]
id            = "acme.push_notifications"
client_type   = "::acme_push::PushClient"
auto_register = false
```

### Por plugin (autor de la app)

```toml
[[app.plugin]]
id            = "istmo.data_store"
auto_register = false
```

El registry omite el plugin; registralo vos después de
`IstmoHost.onCreate(this)` (Android) o dentro de
`IstmoApp.run(registerPlugins:entry:)` (iOS).

### Globalmente

```toml
[app]
auto_register = false
```

Los registries se siguen generando, vacíos.

## Debugging

Si al registry le falta un plugin que esperabas:

- Confirmá que el `istmo.toml` del plugin no tenga `auto_register = false`.
- Confirmá que no tengas un override `[[app.plugin]]` que matchee en tu
  app.
- Confirmá que no estés usando `role = "client"` para ese plugin.
